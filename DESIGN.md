# DESIGN.md — Taint-Tracked Tool Broker (TTTB)

## 0. Status

This document is the complete, implementable architecture for `taint-tracked-tool-broker`, a framework-agnostic TypeScript/Node.js library. It resolves an internal design panel that produced four candidate architectures; this is the synthesized result, not a menu. Where the panel's proposals conflicted, the resolution and the reasoning are stated explicitly in §3.

## 1. Problem Statement

An LLM agent with tool-calling access is dangerous the moment it reads content it did not originate — a fetched page, an email, a file, another tool's output — because at the token level there is no boundary between *data* and *instructions* once both are in context. This is indirect prompt injection. The fix is enforcement at the boundary where the model's decisions become real side effects: the tool call.

TTTB is a broker that every tool call passes through. It must:

1. Attach provenance/taint labels to tool results.
2. Propagate those labels as data flows into later tool-call arguments.
3. Enforce policy at call time — block, warn, or require human approval for privileged sinks (shell, file write, network, email, purchase, code execution) whose arguments (or whose *context*) carry untrusted influence, especially in combination with private-data access and exfiltration capability (Simon Willison's "lethal trifecta").
4. **Survive the one operation that destroys literal taint tracking: the agent reading untrusted content and re-emitting it in its own words.** A broker that only does substring/reference propagation is defeated by "summarize this page, then act on the summary." This is the hardest requirement and the one this document treats as load-bearing, not an afterthought.

## 2. Prior Art & Positioning

- **CaMeL** (Google DeepMind): a privileged planner generates a program; a custom interpreter tags every runtime value; a quarantined, tool-less LLM performs schema-constrained extraction of untrusted content; untrusted data can be a *value* but never *control flow*. Strongest soundness of any prior art here, at the cost of requiring a bespoke interpreter and a plan committed before data is read — a real practicality tax for retrofitting onto an existing OpenAI/Anthropic-style function-calling loop.
- **The lethal trifecta** (Willison): private data + untrusted content + exfiltration capability together is the dangerous combination; any two alone are usually lower-risk. TTTB uses this as an **escalator** on top of a content-agnostic gate, not as the sole gate — see §3 for why treating it as the sole gate is unsound.
- **Dynamic taint tracking / Perl taint mode**: wrap values, propagate on string ops, forbid tainted values at dangerous sinks without explicit untainting. TTTB keeps this as a best-effort, non-load-bearing convenience layer (§4, Layer 1).
- **Classic IFC (Jif, DLM)**: explicit flow (trackable via syntax) vs. implicit flow (information leaked through control-flow decisions conditioned on secret/tainted data). TTTB's central mechanism (§6) is a direct, deliberately coarse answer to implicit flow: it does not try to trace *which* decision was influenced, only *whether* untrusted content was live when a privileged decision was made.

TTTB departs from CaMeL by not requiring a custom interpreter or a frozen program; it departs from pure fingerprint-based taint tracking by **not treating content matching as the safety boundary** — content matching is demoted to an explainability and false-positive-reduction layer, and a structural, content-agnostic scope watermark becomes the actual enforcement mechanism.

## 3. Design Principles (resolving the panel's tensions)

The panel produced four proposals. The winning one (content-addressed fingerprint registry) had the best explainability and practicality, but the judges identified a concrete soundness hole: its policy only escalated untrusted-content-into-exfil-sink calls to `REQUIRE_APPROVAL`/`BLOCK` when a *separate* private-data leg had also fired in-session; absent that leg, a verbatim malicious payload could ride straight into an exfiltration sink under a bare `ALLOW_WITH_WARNING`. A second proposal (session/turn watermark) fixed the paraphrase-survival problem cleanly by gating on *scope exposure* rather than *argument content*, but its own default policy repeated a structurally similar bug: it lumped `exec:shell`/`exec:code`/`write:fs`/irreversible sinks into an "exfil-class" bucket gated by the same private-data-contingent trifecta check at the `DERIVED_UNTRUSTED` tier, so a schema-quarantined payload could reach unconditional shell execution under a bare warning whenever no private-data tool happened to fire first.

This design makes three explicit resolutions:

1. **The scope watermark, not content matching, is the safety boundary.** Every tool call is checked against a monotonic per-scope `TaintWatermark` that the broker raises structurally the instant untrusted content (or a sanctioned quarantine derivative) enters a scope's context — *before* the model gets a chance to transform it. Fingerprint matching (content-addressed hashing/simhash/minhash, from the winning proposal) is retained in full, but reassigned to a secondary role: precise source attribution, audit-quality explanations, and — carefully — eligibility to *downgrade* a verdict's severity when a literal chain is intact. It can never be the sole reason a call is allowed, and it can never *loosen* a verdict the watermark already produced.

2. **Sink severity is keyed off capability class first, private-data-seen second.** `EXEC`-class sinks (arbitrary code/shell execution) are hard-gated by watermark level alone — never contingent on whether a private-data tool happened to fire — because arbitrary code execution needs no private data to be catastrophic. `EXFIL`-class sinks require approval the moment untrusted content is or was live in scope, *regardless* of the private-data leg; `privateDataSeen` is used purely as an **escalator** (bumping `REQUIRE_APPROVAL` to `BLOCK`), matching Willison's framing that the full trifecta is worse than any two legs, without ever letting the two-legs-only case degrade to a silent pass-through. This directly closes the gap both panel proposals shared.

3. **Because the gate is scope-level and content-agnostic, most of the "hard part" is solved by construction, not by cleverness.** Inline paraphrase, translation, and boolean/enum decision-laundering (an untrusted page causing the model to flip a flag with zero tainted text ever appearing in the sink's arguments) are all caught the same way: the sink check never looks at argument content to decide whether to gate, only at whether untrusted content has been in this scope's tracked context. What genuinely escapes detection is narrower and named honestly in §10: content that enters the model's context through a channel the broker never observes at all.

## 4. Taint & Provenance Data Model

Raw JS strings cannot carry metadata. TTTB uses three cooperating layers with a strict authority order: **watermark > fingerprint registry > in-process wrapper**. Each layer degrading does not break the one above it.

### 4.0 A single trust lattice, used everywhere

```
CLEAN (0) < DERIVED_UNTRUSTED (1) < RAW_UNTRUSTED (2)
```

- `CLEAN`: no untrusted content contributed — a developer-declared literal, or a scope after explicit `declassify()`.
- `DERIVED_UNTRUSTED`: content that reached the model exclusively through the sanctioned, schema-constrained quarantine path (§6) — bounded, typed, but still not clean.
- `RAW_UNTRUSTED`: untrusted content is or was live in the scope's tracked context via any other path.

This single vocabulary is used for both the per-scope watermark (Layer 0) and per-record fingerprint trust (Layer 2), eliminating the parallel, inconsistent trust enums the panel's four proposals each invented independently.

### 4.1 Layer 0 — Scope Watermark (the safety boundary)

```
TaintWatermark { level: TaintLevel; privateDataSeen: boolean; sources: ProvenanceTag[] }
TaintScope { kind: 'session' | 'turn'; id: string; watermark: TaintWatermark }
```

A session holds a `sessionScope` and a rotating `turnScope`. `resetScope: 'turn' | 'session'` (configurable; `'session'` is the default for autonomous/unattended agents, `'turn'` an explicit lower-friction opt-in for chat assistants) determines whether the watermark clears at each new user turn. `level` and `privateDataSeen` are **monotonic non-decreasing** within a scope's lifetime; the only way down is `broker.declassify(reason, approvedBy)` — an explicit, audited, human action, never an implicit side effect of an approved call (approving one blocked call does not declassify the scope).

**What counts as "a turn," precisely.** `broker.startNewTurn()` doesn't observe your framework's control flow — it only does what you tell it, when you call it. TTTB's definition of a turn is *one full user-facing exchange*: from the moment a new user message enters the agent loop until that loop has no more pending tool calls and control returns to the user (or the process awaits the next user message). A single turn, by this definition, commonly involves *several* tool calls and *several* underlying model completions — an agentic loop reading a page, then deciding to summarize it, then writing a file, is still one turn, because the user hasn't spoken again in between. The call site that matters is therefore **once, at the top of your loop's handling of each new incoming user message** — never inside the loop's own per-iteration tool-dispatch or per-model-completion logic. Calling it at a finer granularity than that (e.g. once per tool call, or once per model completion within a single multi-step response) resets the watermark *mid-reasoning*, which can silently reopen exactly the exposure the watermark exists to track: a page fetched two tool calls ago in the same logical turn would read back as `CLEAN` to a sink call three tool calls later, purely because something in between happened to call `startNewTurn()`. Calling it too rarely (e.g. never, or only at session start) is safe but forfeits `'turn'` mode's entire usability benefit — GAPS.md #2's cross-turn accumulation just keeps accumulating within what your framework calls a session. `examples/anthropic-tool-loop.ts`'s `runToolLoop()` shows the correct call site concretely: once per `main()`-level invocation, wrapping the whole while-loop that keeps dispatching tool calls until the model stops requesting them — not inside that while-loop's own iterations.

**Implementation note — `resetScope: 'turn-decay'`, a bounded middle ground for GAPS.md #2.** The choice between `'session'` (never clears, unbounded blanket-gating cost) and `'turn'` (clears at the very next turn boundary, an unbounded cross-turn latent-influence gap) is a hard binary with no room to trade a *quantified* amount of one for the other. `resetScope: 'turn-decay'` (with a required `turnDecayWindow: number`) adds a third option: the watermark persists across `turnDecayWindow` consecutive turns with no NEW exposure before clearing, instead of clearing at the first one regardless. `turnDecayWindow: 1` is exactly equivalent to `'turn'` — turn-decay is a strict generalization, not a separate mechanism living alongside it.

Three design choices, each made to keep this auditable rather than to maximize precision:

1. **One decay counter for the whole scope, not one per source.** A per-source sliding decay (each `ProvenanceTag` aging out independently, the watermark level re-derived as the max over only the not-yet-decayed sources) would be more precise — the level could step down as individual old sources expire, rather than the whole episode clearing in one shot. It would also be a fundamentally different and riskier feature: the watermark level is currently monotonic *within* an exposure episode (it only ever moves by an explicit `declassify()` or a full turn-reset, never silently mid-episode) — per-source decay would break that invariant in a way nothing has audited yet. Turn-decay instead keeps the existing "whole episode clears atomically" shape `'turn'` mode already has, just delayed by `turnDecayWindow` turns instead of one.
2. **A NEW exposure resets the counter to itself, not merely fails to advance it.** Exposure at turn N, a second unrelated exposure at turn N+1, no further exposure after that: the decay window restarts counting from N+1, not N. This is what makes the mitigation track the gap's actual shape ("no NEW tool result in between") rather than just relocating the same cliff a few turns later regardless of what happens in between.
3. **`privateDataSeen` decays together with `level`, on the same clock, not independently.** Both fields already live on one `TaintWatermark` and already clear together under `'turn'`/`declassify()` — giving `privateDataSeen` its own independent decay timer would be a second, orthogonal design axis (arguably it should decay *slower*, since the lethal-trifecta risk is about a private-data read combined with a later privileged action) that deserves its own review, not a default bundled silently into this feature's first cut. Named here as a deliberately-not-addressed refinement, not a silent gap.

Implementation-wise, every existing raise call site now goes through one `raiseWatermarkAndResetDecay()` helper (instead of calling the imported `raiseWatermark()` directly) specifically so the counter-reset can't be forgotten at a new call site the way three independent copies of "is this an untrusted source" already once risked drifting (see the reserved-tool-name/`isUntrustedSource()` note above) — and `startNewTurn()`'s 'turn' and 'turn-decay' branches share one `clearScopeForTurnReset()` implementation for the actual clear/plan-reset/audit sequence, so they can't diverge on what "the watermark actually cleared" means or looks like in the audit log.

**The watermark is raised atomically inside `ToolCallBroker.call()`, in the same step that a source tool's result is captured** — before that result is ever handed back to the agent loop for the model to read, let alone rewrite. This is why it survives paraphrase, translation, re-encoding, and decision-laundering: none of those operations happen before the raise; they can only happen after, on a scope whose watermark is already committed.

**Implementation note — concurrency, dual-role tools, and args integrity.** "Atomically ... before that result is ever handed back" is only true if `call()` invocations can't interleave. Adversarial review found a real, reproducible way they could: an agent harness dispatching a model's parallel `tool_use` blocks concurrently (a completely ordinary pattern — `Promise.all([fetchUrl.execute(...), shellExec.execute(...)])`) lets a sink call's gating check read the watermark *before* a concurrently-in-flight source call's `applyPostExecutionEffects` has raised it, since the raise can only happen after that source call's own `execute()` promise resolves. `ToolCallBroker.call()` therefore serializes every invocation on one broker instance through an internal async lock (`Broker.withLock`): each call's entire gate-then-execute-then-raise sequence completes before the next one's gating check runs, restoring the atomicity the design has always claimed, at the cost of no longer running concurrent tool calls in parallel *through this broker* (a real latency cost for, e.g., several independent web fetches in one turn — deliberately accepted; see GAPS.md #13). A tool's own `execute()` calling `broker.call()` again on the same broker (reentrant dispatch) would deadlock that lock, so it is detected via `AsyncLocalStorage` and rejected with `ReentrantCallError` instead of hanging.

**Implementation note — narrowing the lock to a targeted barrier.** The blanket cost named just above ("no longer running concurrent tool calls in parallel through this broker") applies to literally every call, including ones that could not possibly race: a pure-computation utility tool with no sink capability, not a source, reading no private data — e.g. a `calculate` or `get_current_time` tool — gains nothing from the lock and pays its full latency cost anyway under the original design. This was flagged as the highest-risk item in a later improvement-roadmap review specifically because it touches the exact mechanism the paragraph above was written to fix, with an explicit requirement to not reopen that race — so the approach taken here is deliberately the most conservative one that still delivers a real benefit, not a full redesign of the lock's internals.

`call()` now makes one additional, purely-additive check before deciding whether to enter the lock at all: a call is **barrier-exempt** iff `sinkClass === 'NONE'` (so it is never gated — nothing to protect a *read* of the watermark for) AND it is not an untrusted source (`isUntrustedSource(tool)` — so it will never *raise* the level) AND it does not declare `readsPrivateData` (so it will never *set* `privateDataSeen` either). Both the "read" and "write" halves of that check matter: an earlier draft only excluded untrusted sources, missing that a `NONE`-sinkClass tool with `readsPrivateData: true` (e.g. a `read_creds` lookup) still *writes* to the watermark via `applyPostExecutionEffects()`'s `markPrivateDataSeen()` call — exactly the kind of write a later gated call's lethal-trifecta escalation depends on seeing. An exempt call's entire dispatch — no gating (skipped for `NONE` already), `execute()`, and `applyPostExecutionEffects()` (both its conditions provably false) — never reads or writes `this.currentScope.watermark` in either direction. That is what makes this safe *by construction*, not by argument about scheduling: a call that is proven to touch none of the shared state the lock protects cannot participate in a race over that state, regardless of how its execution interleaves with anything else. Everything else — any call with a real sinkClass, any untrusted source, any private-data reader — goes through `Broker.withLock` completely unchanged: the same single FIFO queue, same synchronous queue-position capture at invocation time (before the exemption check's own tool lookup, which is itself synchronous), same reentrancy-guard wrapping. The exemption check adds a bypass; it does not touch the lock's own logic for anyone still using it.

An unknown tool name is deliberately never exempt (a missing tool fails the `tool &&` guard in `call()`, not the exemption predicate) — it still falls through to `dispatch()`'s own `UnknownToolError`, inside the lock, exactly as before; there was never a reason to special-case it for speed.

The "touches none of the shared state, by construction" claim two paragraphs up needed one correction once GAPS.md #17 was fixed — see the implementation note below for what was missing and how `mayCallSummarize` closes it.

**Implementation note — fixing GAPS.md #17, and a second interaction the barrier-exemption feature above turned out to have.** `broker.summarize()` raises the watermark through the identical `raiseWatermarkAndResetDecay()` helper every other raise site uses, but — until now — was a standalone function that never went through `call()`'s own reentrancy check or `Broker.withLock`, for exactly the deadlock reason named when GAPS.md #17 was first written: naively wrapping it in the same lock would deadlock the moment `summarize()` is called reentrantly from inside a tool's own `execute()` (the documented fetch-and-quarantine composite pattern, §6.2), since the outer call would already be holding the lock `summarize()` was trying to acquire.

The fix reuses `reentrancyGuard` (already `AsyncLocalStorage`-based) rather than adding a second mechanism: its stored value changed from a bare `true` to `{ lockHeld: boolean }`, set by `call()` to `{ lockHeld: true }` when it acquires `withLock` and `{ lockHeld: false }` when it takes the barrier-exempt bypass instead. `summarize()` is now wrapped: if `reentrancyGuard.getStore()?.lockHeld` is true, it raises inline — no new lock needed, the call already holds it, and this is exactly the deadlock-avoidance case above. Otherwise (genuinely top-level, or nested inside a barrier-exempt call) it acquires `withLock` itself, exactly like a fresh `call()` would, closing the original race: a `summarize()` invoked concurrently with a `call()` now has the same synchronous, invocation-order queue-position capture either way.

Writing the adversarial test suite for this (`test/broker.spec.ts`'s "broker.summarize() / broker.call() serialization" block) surfaced a second, genuinely new problem, not merely a variant of the first: a composite tool whose `execute()` calls `broker.summarize()` internally, if it were barrier-exempt (a real possibility — such a tool is typically `sinkClass: 'NONE'`, not `isSource`, and reads no private data, exactly the exemption's criteria) and did any real async work (e.g. its own fetch) *before* reaching the `summarize()` call, was **not** actually protected by the fix above. By the time `summarize()` finally ran and tried to acquire the lock, a concurrently-dispatched gated call could already have completed its gating check — because the *outer* exempt call, per the barrier-exemption design, never reserved a lock position at all, and nothing else did on its behalf during that intervening async gap. A test written to *confirm* the fix (with an artificial delay standing in for that real async work, modeling an actual composite tool honestly rather than a best-case instant one) failed, catching this before it shipped.

The barrier-exemption predicate cannot detect this case by inspecting a tool's declared shape — `sinkClass`, `isSource`, `readsPrivateData` say nothing about what an `execute()` function body actually does at runtime, and `broker.summarize()` is a public method any tool's closure can reach regardless of how that tool is registered. So `ToolExecutor` gained one more declaration, `mayCallSummarize?: boolean`, and `isBarrierExempt()` now also requires `!tool.mayCallSummarize`. This is the same trust boundary `isSource`/`trusted`/`readsPrivateData` already rest on (GAPS.md #10: the library enforces based on what the integrator declares, and cannot verify the declaration against the tool's real behavior) — not a new category of risk, but it is a new place that trust boundary applies, so `docs/classifying-tools.md` gained a fifth question naming it directly. `test/broker.spec.ts` keeps both directions honest: one test proves a correctly-declared (`mayCallSummarize: true`) composite tool is protected; a second, explicitly labeled test proves a misdeclared one is not, and asserts that as the documented actual behavior rather than quietly hoping nobody hits it.

This shipped only after an adversarial test suite specifically built to try to reopen the original race through the new exemption logic (`test/broker.spec.ts`'s "barrier exemption" describe block): the original regression test unchanged; a timing-based proof that an exempt call genuinely does not wait behind a slow, concurrently-dispatched gated call (the actual point of this change, not just its safety); the private-data-reader case above, raced against a later gated call under `Promise.all` exactly like the original bug's own reproduction; reentrancy from *within* an exempt call's `execute()`; an unknown tool name raced against a real gated pair; and a 25-iteration stress mix of exempt/raiser/gated calls checked for a deterministic outcome on every run. All green, including five repeated full-suite runs specifically to catch timing-dependent flakiness before this was considered done.

A second, distinct hole the same review found: a tool honestly declaring **both** `isSource: true` (not `trusted`) **and** a non-empty `capabilities` array — a realistic shape ("fetch a page and forward it", "download and run a script") — could read untrusted content and act on it *within one call*, gated only by the watermark as it stood *before* that call, since nothing had raised it yet for content this same call was about to introduce. Serializing calls does not fix this (there is no earlier call to serialize against). `register()`/`wrap()` therefore reject such dual-role tools outright (`DualRoleToolError`): split the fetch and the privileged action into two separate broker-mediated calls, mark the source `trusted` if it genuinely isn't attacker-influenceable, or use the fetch-and-quarantine pattern in §6.2's implementation note.

Third: `call()`'s `args` object is handed to the policy function, the approval channel, `execute()`, and the audit sink. If those all shared one live, caller-owned reference, a tool that mutates its own args in place (an ordinary pattern — e.g. appending a delivery receipt) — or any code racing the approval-wait window — could make what a human approved, what actually ran, and what got audited silently diverge. `call()` snapshots `args` once (`structuredClone` by default, into `argsSnapshot`) for the `ToolCall` used by policy/approval/audit. `structuredClone` throwing (functions, most class instances, `WeakMap`/`WeakSet` in the args) now fails the call loud, with `NonCloneableArgsError`, instead of silently dispatching on a shared live reference — the earlier fallback quietly reopened exactly the divergence this snapshotting exists to close (GAPS.md #16). `createBroker({ cloneArgs })` lets an integrator supply their own cloning function for tools that genuinely need a non-JSON-able argument type — including `jsonSafeClone` (`src/json-safe-clone.ts`), a faster alternative for the common case where args really are plain JSON: `structuredClone` runs Node's general structured-clone algorithm (cycle detection, `Map`/`Set`/`Date`/`RegExp`/typed-array support) that realistic tool-call args rarely need, and `bench/args-clone.ts` (`npm run bench`) measures this at 4–100×+ faster across representative args shapes. It clones only plain objects/arrays/JSON-safe primitives and throws — never silently misrepresents — on anything else (a naive recursive clone of a `Date` would silently produce an empty `{}`, since a `Date`'s time value isn't an enumerable own property; this fails loud instead, the same GAPS.md #16 philosophy applied to a second cloner). `ApprovalChannel.requestApproval` also now receives the full `REQUIRE_APPROVAL` decision (not just its reason string), so an implementation can bind its response to `decision.approvalToken` instead of trusting that whatever comes back corresponds to this particular request.

`execute()` itself used to get a SEPARATE, independently-derived clone — re-cloned from the live `args` reference at the moment `execute()` was actually called, not from `argsSnapshot` — rather than a defensive clone of `argsSnapshot` itself. This was believed fixed here at the time but was not: a caller that kept a reference to the object it passed to `call()` and mutated it later (an entirely realistic pattern — reusing a request object across retries, say) could change what actually executed without changing what the approval channel was shown or what got audited, since only the SECOND clone tracked the live object. Actually fixed as part of the implementation note directly below, alongside two related races found by the same review pass: `execute()` (on every path — `ALLOW`, `ALLOW_WITH_WARNING`, and an approved `REQUIRE_APPROVAL`) now always clones from `argsSnapshot`, never from `args`, so there is exactly one frozen source of truth for "what was requested" from the moment `dispatch()` captures it.

**Implementation note — a stale gating decision could still execute; and `REQUIRE_APPROVAL` held the whole-broker lock for the entire wait.** Two independent adversarial-review passes (a comprehensive full-repo review and a second, deliberately different-in-kind one — active exploit construction, concurrency stress, DoS/resource-exhaustion) found that a gated call's `TaintContext`/`PolicyDecision` is computed once, early, but nothing re-checked it against the CURRENT watermark immediately before `execute()` actually ran — and the watermark can move during either of two async gaps between that computation and execution:

- `markContextExposure()` (and its three specializations) is a deliberately synchronous escape hatch (GAPS.md #1) that never acquires `Broker.withLock` — it can land at any point control yields to the event loop, including mid-`await` inside a slow custom `PolicyFn`, or during a `REQUIRE_APPROVAL` wait.
- Before this fix, `REQUIRE_APPROVAL` awaited `ApprovalChannel.requestApproval()` — a potentially human-timescale operation — WHILE still holding `Broker.withLock`, freezing every other call on the broker for the full wait. A concurrently-dispatched source call raising the watermark during that freeze couldn't even get a gating check in edgewise until the wait resolved.

Either gap lets a decision computed against a now-stale, too-permissive `TaintContext` still execute: approve at `DERIVED_UNTRUSTED`, have the scope escalate to `RAW_UNTRUSTED` during the wait (an unconditional `BLOCK` tier for `EXEC`), and the stale approval still runs. `dispatch()`'s gated path is now split into three steps — `gateDecision()` (compute the decision, under the lock), an unlocked wait for `REQUIRE_APPROVAL` only, and `finalizeGated()` (execute, under the lock again) — with `revalidateBeforeExecute()` as the checkpoint that actually closes both races: immediately before ever calling `execute()`, it re-checks the watermark against the snapshot `gateDecision()` captured; if it moved, the original decision is discarded and a FRESH one is computed against the current state instead of trusted blindly. This is deliberately bounded to one extra round, not a loop — a fresh `REQUIRE_APPROVAL` is never re-prompted (there is no fresh human grant for it) and is conservatively treated as not approved.

Splitting into three steps only matters — only needs to release the lock at all — when there IS a `REQUIRE_APPROVAL` wait to release it around. The first implementation released the lock between `gateDecision()` and `finalizeGated()` unconditionally, even for the ordinary `ALLOW`/`BLOCK`/no-approval-needed case, which reopened a DIFFERENT, older problem: a second call queued behind the first on the lock could now interleave in that gap and run out of invocation order, breaking the "gates correctly regardless of which call is listed first in `Promise.all`" guarantee the very first concurrency fix (two notes above) exists to provide. Caught by that exact regression test. Fixed by keeping `gateDecision()` and `finalizeGated()` inside ONE unbroken `withLock()` hold whenever `decision.action !== 'REQUIRE_APPROVAL'`, and only splitting into the three-step, lock-released form when an approval wait is actually going to happen.

**Implementation note — one broker instance is one session, not enforced, only documented (GAPS.md #19).** The same review passes found nothing stopping an integrator from constructing a single `Broker` and routing two different, concurrent, unrelated agent sessions' tool calls through it — every safety guarantee here (the watermark, the Layer 2 registry, `withLock`'s ordering) is per-instance in-memory state, so doing this doesn't fail loudly: it either serializes unrelated sessions' calls against each other (an availability cost) or, worse, lets one session's exposure silently raise the watermark gating the other session's calls (a soundness cost, in either direction — spurious over-restriction, or an integrator working around that friction by loosening policy for the shared instance and reopening the isolation both sessions needed). Not something `call()` can detect from inside itself (a `Broker` has no way to know how many logical sessions its caller intends), so this is fixed the same way GAPS.md #10's sink-misclassification and #17's `mayCallSummarize` trust boundaries are: `createBroker()`, `BrokerOptions.sessionId`, and the `ToolCallBroker` interface itself now carry prominent doc comments stating the rule and why violating it is unsafe, not merely unconventional.

**Implementation note — four more findings from the same passes, smaller in scope but real.** `wordShingles()` (`taint/fingerprint.ts`) used to fall back to treating an entire short text (under `SHINGLE_WIDTH` = 5 words) as a single shingle — meaning two near-identical short texts differing only by word order, or by one word, scored EXACTLY 0 overlap, a full miss rather than a partial one, for exactly the shortest and most common realistic payloads (a URL, an account number, a short instruction). Now shingles at the largest narrower width that still yields overlapping windows (GAPS.md #8 has the fix's own remaining-limitation note). `InMemoryTaintRegistry`'s LSH-band/shingle candidate-gathering had no bound on the CANDIDATE set it scores before applying `maxMatches` — a registry with a large cluster of near-duplicate or coincidentally-colliding records could make a single band/shingle bucket collect a large fraction of the whole registry, silently degrading a lookup back toward the linear-scan cost the indexing exists to avoid; `maxFuzzyCandidatesPerLookup` (default 2000) now bounds that directly (GAPS.md #13). `scanArgsForTaint()`'s tree walk, `findOutboundHosts()`'s egress scan, and the standalone `diffProposedArgs()` utility all recursed with no depth bound — a sufficiently deep args tree (nested objects/arrays forwarded from a prior tool's own deeply-nested result) would overflow the JS call stack with an unpredictable-depth `RangeError`, and on the mandatory scan path, with zero audit trail; all three now throw `ArgsTooDeepError` at a fixed depth of 500, audited as a `BLOCK` on the broker path (GAPS.md #13). Last, `ToolExecutor.trusted`'s own doc comment used to frame it as "deterministic/pure tools may opt out" — misleading, since determinism has nothing to do with whether a tool's content is attacker-influenceable — and `docs/classifying-tools.md`, the worked-examples checklist both this doc and README.md point to, was missing from `package.json`'s `files` allowlist entirely, so an installed copy of the package couldn't resolve that link (GAPS.md #10).

**Implementation note — restoring watermark state across a process boundary.** `createBroker({ initialWatermark })` seeds a fresh broker's scope with a previously-exported `TaintWatermark` instead of starting `CLEAN`. `TaintWatermark` is already a plain JSON-able object (a `TaintLevel` string, a boolean, and an array of plain-field `ProvenanceTag`s), so no special decoding is needed for this half of a broker's state — see §4.2's persistence note for the registry half, and `src/persistence.ts` for both combined. This directly addresses the "how would an integrator even restore this" half of GAPS.md #12; it does not and cannot make restoration automatic — something still has to call these APIs and thread the result to the next process or agent.

**Implementation note — audit completeness.** A later gap-audit pass found that not every watermark-affecting operation reached `AuditSink`, despite §6.2 already documenting `broker.summarize()` as "auditable ... like any other call": `summarize()` itself, `markContextExposure()` (the manual escape hatch for GAPS.md #1's untracked-channel gap), and an ordinary source-tool call raising the watermark or the `privateDataSeen` flag (the `sinkClass === 'NONE'` branch of `dispatch()`, which is never policy-gated and — correctly, for a plain no-op call — was never audited either) all mutated safety-relevant state with zero audit trail. That meant an integrator reviewing `auditSink` for "what happened in this session" saw every gated privileged call but had a structural blind spot around exactly the events that explain *why* later calls got gated: the exposure itself, the manual override for an exposure the library couldn't detect on its own, and every use of the sanctioned tier-downgrade path. All three now emit an `AuditEvent` (`ALLOW_WITH_WARNING` for the exposing/downgrading event itself, `BLOCK` for a rejected `summarize()` input) — `markContextExposure()`'s event is recorded under the synthetic tool name `__tttb_context_exposure`, mirroring `declassify()`'s existing `__tttb_declassify` and `summarize()`'s `__tttb_summarize`. A NONE-sinkClass call that neither raises the watermark nor sets `privateDataSeen` (a genuine no-op, or a `trusted` source) is still not audited — nothing safety-relevant happened, so there is nothing to explain later.

The same pass also found that `declassify()` — already audited before this — recorded an event that was technically present but forensically empty: `scopeLevel` was hardcoded to the post-clear `CLEAN`, true of every declassify() call and so telling an investigator nothing about what was actually cleared. It now snapshots the watermark's level/`privateDataSeen` *before* `declassifyScope()` mutates them and records that prior state instead, so an audit-log reviewer can see not just "a human declassified this scope" but "a human declassified this scope out of `RAW_UNTRUSTED`."

**Implementation note — a multi-agent improvement-roadmap pass surfaced four more real bugs.** Asked what could be added or improved, an independent 8-lens review (architecture, testing, docs, DX, ecosystem, performance, and a fresh security red-team pass) turned up several genuine defects, four of them small and unambiguous enough to fix immediately rather than merely propose:

1. **`scanArgsForTaint()`'s tree walk had no cycle guard.** A circular args object — reachable in practice, not just in theory, since `structuredClone` (used to snapshot args) happily tolerates cycles — recursed forever and crashed the broker with an uncaught `RangeError`, before the plan-freeze check, before the policy decision, and before any `AuditSink.record()` call: the one rejection path in the whole design with zero audit trail. Fixed with a `WeakSet`-based visited-node guard: an already-visited object is skipped, not re-scanned, which loses no coverage (a cycle can only make the same subtree reachable twice, never expose content that wasn't already scanned on its first visit).
2. **A non-JSON-safe source-tool result could suppress the watermark raise entirely.** `applyPostExecutionEffects()` called `toRegistrableText(result)` unguarded; a circular or otherwise-unserializable result (a realistic shape for, e.g., a raw HTTP-client/response object) threw from `JSON.stringify` *after* the tool's real side effect had already happened but *before* `raiseWatermark()` ran — silently leaving Layer 0 at whatever it was before, for content that had genuinely just been read. This directly violated the design's own stated principle that Layer 2 (fingerprinting) is best-effort and must never be load-bearing for Layer 0 (the watermark): a Layer-2 serialization failure was taking Layer 0 down with it. Fixed by making the raise unconditional and the registration best-effort — a non-serializable result still raises the watermark (with a random id in place of a content hash, since there's no content hash to compute), it just skips the Layer 2 fingerprint record.
3. **`startNewTurn()`'s reset was incomplete.** In `resetScope:'turn'` mode it replaced the scope with a fresh `CLEAN` one but never touched `this.plan`/`this.planCursor` (§11) and recorded no `AuditEvent` for whatever watermark it discarded. Stale plan state surviving a turn boundary can only ever cause spurious over-blocking in a later, unrelated turn (plan-freeze is additive, so it can't create a bypass) — but it's still a real footgun, and discarding a genuinely non-`CLEAN` watermark with no audit trail is exactly the moment GAPS.md #2's cross-turn risk crystallizes. Fixed: the plan resets alongside the scope, and a discarded non-`CLEAN` watermark is now audited under `__tttb_turn_reset` (mirroring `declassify()`'s pattern above) — an already-`CLEAN` scope resetting stays silent, so ordinary per-turn resets don't add audit-log noise.
4. **`TaintRegistry.restore()` didn't merge monotonically like `register()` does.** `register()`'s dedup path explicitly never lets a later, weaker registration downgrade an existing record (`test/registry.spec.ts` even names this invariant directly) — `restore()`'s id-collision path did a wholesale replace instead, so restoring a stale exported snapshot into a registry that had since re-confirmed that content more strongly could silently downgrade it. Fixed to merge `level`/`sensitivity` the same way `register()` does, keeping `restore()` and `register()`'s collision semantics consistent.

None of these are content-matching evasions or gating-policy holes — they're robustness/consistency defects in code paths adjacent to the safety-critical ones, the same category as everything found in the original adversarial-review pass above. A fifth, more architecturally significant finding from the same pass — `broker.summarize()` is not serialized against `broker.call()` through the same lock (§ above), so a concurrently-in-flight `summarize()` and a gated sink call can race the same way the original concurrency bug did — was deliberately **not** fixed here: naively wrapping `summarize()` in `withLock()` would deadlock the documented fetch-and-quarantine composite-tool pattern (§6.2) if `summarize()` is ever called reentrantly from inside a tool's own `execute()`, so it needs the same reentrancy-aware treatment `call()` already has, not a copy-paste of the lock. Tracked at the time as a known, real, unfixed race, not silently left off this list — since fixed; see the "fixing GAPS.md #17" implementation note further down for the reentrancy-aware treatment this needed, and a second interaction it surfaced with the barrier-exemption feature below.

**Implementation note — reserved synthetic tool names, and deduplicating the "trivial audit event" shape.** The synthetic tool names introduced above (`__tttb_context_exposure`, `__tttb_turn_reset`, `__tttb_declassify`, `__tttb_summarize`) let an `AuditSink` consumer tell a library-generated administrative event apart from a real tool call — but nothing previously stopped an integrator from `register()`-ing an actual tool under one of those exact names, which would make its audit events genuinely indistinguishable from the broker's own. `register()`/`wrap()` now reject any tool name starting with the reserved `__tttb_` prefix (`ReservedToolNameError`, `src/internal-audit.ts`). Separately, the ~6-7 call sites across `broker.ts`/`quarantine.ts` that build these administrative `AuditEvent`s had each hand-written the same "no sink, no fingerprint match, only ambient scope state" `TaintContext` shape (`matchedRecords: []`, `argFingerprintFloor: 'CLEAN'`, `sinkClass: 'NONE'`) and the same "is this tool an untrusted source" check (`tool.isSource && !tool.trusted`, independently re-derived in `register()`'s dual-role check, `applyPostExecutionEffects()`'s raise, and `dispatch()`'s escalator-audit reason) — three places that could in principle drift out of sync with each other despite meaning the same thing. Both are now pulled into `src/internal-audit.ts` (`trivialTaintContext`/`recordTrivialAudit`, `isUntrustedSource`) and shared. Pure internal deduplication — no behavior change to any existing audit event's content, aside from the new `ReservedToolNameError` rejection itself.

**Implementation note — a convenience API surface over the same primitives, no new gating behavior.** A second quick-wins batch added several thin wrappers, all implemented purely in terms of `register()`/`wrap()`/`call()`/`markContextExposure()` above — nothing here changes what gets gated or how: `callSafe()` (resolves a `CallResult` instead of throwing, for call sites that would rather branch on `ok` than wrap every `call()` in try/catch), `registerAll()`/`wrapAll()` (bulk-register/wrap a name -> tool record, returning the same keys mapped to wrapped executors for `wrapAll()`), `defineSource()`/`defineSink()` (`src/define.ts` — pure object-literal sugar for the two common `ToolExecutor` shapes; `register()`/`wrap()` still do all real validation on what they hand back), and `markToolDescriptionExposure()`/`markSystemPromptExposure()`/`markPastedContentExposure()` (named `markContextExposure()` specializations for GAPS.md #1's three canonical channels — `examples/mcp-integration.ts`'s rug-pull guard now calls `markToolDescriptionExposure()` directly instead of hand-building the `markContextExposure()` call).

The one genuinely new piece is `registerRawForQuarantine()`, which operationalizes the fetch-and-quarantine composite-tool pattern this document has referenced by name several times without a concrete helper: it registers a source-only tool and returns a wrapper whose `execute()` resolves to `{ text, taintRecordId }` instead of just the raw result, so a caller doesn't have to separately recompute or look up the fetched content's fingerprint id to pass as `summarize()`'s `sourceTaintRecordId`. Writing this surfaced a real bug before it shipped: an earlier draft let the wrapped tool opt into `trusted: true` (mirroring `ToolExecutor.trusted`), but a `trusted` source is never registered into the fingerprint registry at all (§4.1's `applyPostExecutionEffects` only registers `isUntrustedSource(tool)` results) — so there was never a `taintRecordId` to hand back, and the helper would throw `QuarantineSourceUnavailableError` on every call for a `trusted` source, caught by this batch's own tests. Fixed by removing `trusted` from `RawQuarantineSourceTool` entirely rather than supporting a combination that can never work: this helper exists specifically to feed untrusted content into `summarize()`, and a genuinely trusted source doesn't need quarantining in the first place — register it normally instead. The lookup itself deliberately re-fetches the actual registered record (`registry.lookupExact(text)`) rather than re-deriving an id independently, the same "don't let two derivations of the same fact drift apart" lesson as `isUntrustedSource()` above.

**Implementation note — framework-integration examples.** `examples/langchain-integration.ts`, `examples/vercel-ai-sdk-integration.ts`, and `examples/openai-agents-sdk-integration.ts` demonstrate the same `broker.wrap()` interposition `examples/anthropic-tool-loop.ts` and `examples/mcp-integration.ts` already show, expressed through three popular agent frameworks' own tool-definition idioms (a `name`/`description`/schema object plus an async execute function — LangChain's `tool()`/`Runnable.invoke()`, the Vercel AI SDK's `tool()`/`execute()`, and the OpenAI Agents SDK's `tool()`/`execute()`) instead of a raw `ToolExecutor` or the Anthropic Messages API's `tool_use`/`tool_result` blocks. None of the three depends on the real `langchain`/`ai`/`@openai/agents` packages — each uses a small structural stand-in for that framework's real shape, the same "the pattern is what matters, not fidelity to a fast-moving package's exact current types" stance `anthropic-tool-loop.ts`'s own `MockAnthropicClient` already takes, and for the same reason: pinning example code to a specific version of someone else's fast-moving SDK would make these examples a maintenance liability without adding anything the wiring pattern itself doesn't already show. Two of the three exercise the `BLOCK` path (an `EXEC` sink, unconditionally gated); `openai-agents-sdk-integration.ts` deliberately exercises `REQUIRE_APPROVAL` instead via `createDeferredApprovalChannel()`, since a real integration has to handle both outcomes and the other two framework examples already cover the first.

**Implementation note — the same MCP pattern against a real SDK, not just the stand-in.** `examples/mcp-integration.ts`'s `McpClient` stand-in exists on the stated theory that the wiring pattern matters, not fidelity to a fast-moving package's exact current types (the same stance the framework-integration examples above take). `examples/mcp-sdk-integration.ts` exists to confirm that theory actually holds rather than leaving it asserted: it wires the identical `broker.wrap()`-around-`tools/call` and `markToolDescriptionExposure()`-on-`tools/list`-change pattern against a genuine `@modelcontextprotocol/sdk` `McpServer` and `Client`, connected via the SDK's own `InMemoryTransport.createLinkedPair()` (a pair of in-process transports the SDK ships specifically for tests like this one) so it stays offline like every other example while still doing real JSON-RPC request/response and a real server-side `RegisteredTool.update()` rug pull rather than a mock swapping a value in a `Map`. One real constraint this surfaced: the SDK only forwards a tool call's arguments to its handler at all when the tool was registered with a real Zod `inputSchema` — a tool registered with no `inputSchema` gets invoked with no arguments regardless of what the caller sent (`server/mcp.js`'s `executeToolHandler`), so this example (unlike the mock) needs `zod` to build those schemas. Both `@modelcontextprotocol/sdk` and `zod` are devDependencies used only by this one example file — the library's own runtime dependencies remain empty, since `package.json`'s `files` field never ships `node_modules` and nothing under `src/` imports either package.

**Implementation note — two Layer 2 performance quick wins, both behavior-preserving.** `scanArgsForTaint()`'s hot path (`checkStringLeaf()`) called `registry.lookupExact(text)` and then unconditionally `registry.lookupFuzzy(text)` for every string leaf — the latter internally calls `buildFingerprint(text)`, which redundantly recomputes the exact SHA-256 hash `lookupExact()` had just computed a moment earlier. `TaintRegistry` gained an optional `lookupCombined(text, opts?)` method (optional so an existing custom `TaintRegistry` implementation that only implements the required `lookupExact`/`lookupFuzzy` keeps compiling and working unchanged, just without the saving); `InMemoryTaintRegistry` implements it by building the fingerprint once and sharing it between the exact check and the fuzzy scoring pass (factored into a shared private `fuzzyMatchesForFingerprint()` so `lookupFuzzy()` and `lookupCombined()` can't drift apart on scoring logic). `scanArgsForTaint()` uses it when the registry provides it, falling back to the two separate calls otherwise — every existing test passed unchanged after this refactor, confirming it's a pure performance change.

Second: `lookupFuzzy()` previously returned every candidate that passed its threshold, unbounded — a registry holding many attacker-chosen near-duplicate records (a realistic adversarial shape, since Layer 2 content is exactly what an attacker controls) could make a single fuzzy lookup return an arbitrarily large `TaintMatch[]`, which then flows into `TaintContext.matchedRecords`, the audit log, and any approval UI. `FuzzyLookupOpts` gained `maxMatches` (default 20); `scanArgsForTaint()` separately caps its own tree-wide aggregate at 50. Both caps had to be done carefully to preserve a real safety property: `TaintContext.argFingerprintFloor` (and `ScanResult.floor`) is the union of every matched record's level, and Layer 2 can only ever *tighten* a verdict, never loosen one — so a naive score-only truncation could silently drop the one match carrying the highest taint level, quietly weakening a verdict that used to be correctly floored. Both caps sort by taint level first, raw score second, before truncating: the single highest-severity candidate is therefore guaranteed to survive any cap ≥1, so truncation can only ever discard lower-value explainability detail, never a floor-raising match. `scanArgsForTaint()`'s own cap is even safer by construction — `floor` there is accumulated independently via `bump()` during the tree walk, not re-derived from the final `matches` array, so its cap cannot affect the floor at all, only the size of the returned list. Both new tests construct an explicit case where a lower-scoring-but-higher-level record would have been dropped by a naive score-only sort, confirming the guarantee rather than just asserting a count.

### 4.2 Layer 2 — Content-Addressed Fingerprint Registry (precision & explainability)

Every tool result and every sanctioned quarantine output is decomposed into a `Fingerprint {exactHash, simhash, shingleHashes, length}` and stored as a `TaintRecord {id, provenance, level, sensitivity, fingerprint, derivedFrom?, confidence}` in a `TaintRegistry`. Before every tool dispatch, `scanArgsForTaint(args)` walks the JSON-able argument tree and, for every string leaf (or ≥40-char substring window), attempts exact-hash lookup, then simhash lookup (Hamming distance ≤3, tunable), then LSH-banded minhash/shingle lookup (overlap coefficient ≥0.6, tunable via `FuzzyLookupOpts.overlapMin`). This produces `TaintMatch[]` with a `matchType` and confidence score, giving precise "this argument literally contains text from `fetch_url(evil.example)`" explanations whenever a literal or near-literal chain survives.

This layer is exactly the winning proposal's mechanism, unchanged in its mechanics — what changes is its **authority**: it feeds `TaintContext.argFingerprintFloor`, which the policy function may use only to *tighten* a verdict (floor it at `REQUIRE_APPROVAL` even if the watermark alone would have allowed a call — the belt-and-suspenders case of a turn-scoped watermark having reset while a fingerprint match still ties an argument to an untrusted source) or to justify a documented *downgrade* within an already-gated tier (see §6). It is never consulted to decide whether to gate a call in the first place; that decision belongs to the watermark alone.

**Implementation note — indexed lookup and eviction (GAPS.md #13).** `InMemoryTaintRegistry.lookupFuzzy()` does not scan every stored record. Candidates come from two indexes populated at `register()` time: an LSH-banded simhash index (the 64-bit simhash split into 8 bands; a query probes its own 8 band buckets, which is guaranteed by pigeonhole to surface every record within `simhashMaxDistance < 8` of it — comfortably covering the default threshold of 3) and a plain shingle inverted index (exact, not approximate — `overlapCoefficient()` is 0 for any pair sharing no shingle, so this index cannot miss a real candidate). Either index only narrows which records get the same exact `hammingDistance()`/`overlapCoefficient()` scoring a linear scan would have computed; thresholding and ranking are unchanged. An optional `maxEntries` (`new InMemoryTaintRegistry({ maxEntries })`) evicts the oldest-*registered* record — not the least-recently-*looked-up* one — once exceeded; re-registering already-known content does not refresh its position, so eviction order stays simple to audit. Unbounded by default. Eviction only removes a record from Layer 2's index; it can never affect the Layer 0 watermark, so the worst case is losing a future attribution/tightening opportunity (GAPS.md #8), never opening a gate.

**Implementation note — fixed-size MinHash sketches were investigated for `shingleHashes` and deliberately NOT shipped.** Each `TaintRecord.fingerprint.shingleHashes` currently stores the record's *full* deduplicated shingle set — memory proportional to document length, unbounded per record (a second, independent cost from the `maxEntries` record-*count* bound above). Replacing it with a fixed-size K-value MinHash signature per record is the standard technique for bounding that, and was prototyped and measured (`bench/minhash-sketch-tradeoff.ts`, `npm run bench:minhash`) rather than shipped speculatively — the result was decisive enough not to ship it.

The prototype gave MinHash every reasonable advantage: rather than a naive Jaccard-similarity swap (the wrong measure for containment on its own — Jaccard is dominated by whichever set is larger, exactly the failure mode `overlapCoefficient()`'s own doc comment names), it kept each record's exact shingle *count* alongside the K-value sketch and analytically recovered the overlap coefficient from the MinHash-estimated Jaccard plus the two exact counts. Tested against the precise scenario `overlapCoefficient()` exists to catch — a short malicious excerpt (here, ~18 shingles) embedded inside a much larger document — at realistic size ratios, with 300 independently-seeded trials per (ratio, K) configuration to measure variance rather than reporting one lucky/unlucky draw:

| blob/excerpt ratio | document shingles | exact `overlapCoefficient()` | K=128 false-negative rate | K=256 | K=512 |
|---|---|---|---|---|---|
| 10× | 211 | 1.00 | 6% | 2% | 0% |
| 50× | 971 | 1.00 | 31% | 14% | 8% |
| 200× | 3,821 | 1.00 | 52% | 27% | 31% |
| 500× | 9,521 | 1.00 | 79% | 61% | 35% |

"False-negative rate" is the fraction of the 300 trials where the MinHash-derived estimate fell below the production `overlapMin` threshold (0.6) despite the true overlap coefficient always being 1.0 (the excerpt is verbatim inside the document in every trial). A 500-word injected excerpt inside a 5,000-10,000-word fetched article — an entirely ordinary size ratio for a real web page — misses the match roughly a third of the time even at K=512, a sketch size already large enough to mostly defeat the memory-bounding this was supposed to buy. The reason is structural, not a tuning problem: MinHash's collision probability for one hash function is ~|A|/|B| when |A|≪|B| (a classic minhash Jaccard-estimator property), so the *expected number* of colliding sketch positions out of K stays a small fraction even at generous K once the size ratio is large enough — and that's before accounting for how a single random extra collision (equally due to chance) swings the analytically-recovered overlap coefficient by a large amount at this end of the range, which is exactly the high-variance shape the mean/min spread in the raw trial data shows.

This is a real, measured regression against a currently-passing, currently-corpus-tested detection property (`light-reformat-evasion`'s own case is exactly this shape), not a theoretical concern — the kind of finding this project ships as an honest "investigated, didn't ship" note rather than either silently declining the idea or shipping it anyway once work had started on it (the same standard applied, with the opposite outcome, to GAPS.md #17's lock race — investigated, and in that case fixable, so fixed; see that implementation note further down). `maxEntries` remains the supported way to bound registry memory — it trades total attribution *history* (older records evicted wholesale) for zero per-match accuracy cost, instead of trading accuracy on every match the way a sketch would. `bench/minhash-sketch-tradeoff.ts` stays in the repository, not deleted after the decision, so this is reproducible rather than merely asserted, and so a future attempt at the same idea starts from real numbers instead of repeating the investigation from scratch.

**Implementation note — cross-process persistence (GAPS.md #12).** The registry deliberately never stores raw plaintext, so exporting/restoring it can't be "re-fingerprint the text on the other side" — it has to move the `TaintRecord`s themselves. Two new `TaintRegistry` methods make this possible without reaching into implementation internals: `entries()` (every stored record, oldest first) and `restore(record)` (insert an already-built record directly, bypassing `register()`'s text-based fingerprinting). A `TaintRecord`'s fingerprint has two fields `JSON.stringify` can't round-trip — `simhash` (`bigint`) and `shingleHashes` (`Uint32Array`) — so `src/persistence.ts` provides `serializeRegistry()`/`restoreRegistry()` to convert those to and from a JSON-safe shape, plus `serializeBrokerState()`/`restoreBrokerState()` combining a registry export with the watermark (§4.1) into one object ready for `JSON.stringify()` and back into `createBroker()` options. See `test/persistence.spec.ts` for a worked round trip through an actual `JSON.stringify`/`JSON.parse` boundary.

### 4.3 Layer 1 — In-Process Wrapper (best-effort fast path)

`TaintedValue<T>` (boxed value + `level`/`sources`) is returned by `broker.wrap(executor)` to callers who want cheap, exact, same-object-identity propagation. Broker-supplied helpers (`concatTainted`, `taintAwareJSONStringify`, `spreadTainted`, `mapTainted`) propagate it through concatenation, JSON round-trips, spread, and map. This layer is documented as **degrading silently** the moment code uses raw `+`, untagged template literals, `JSON.stringify` directly, or — by construction — the moment content passes through the LLM (a fresh generation shares no object identity with anything). None of this matters for soundness: Layer 0 already committed the watermark before any of these operations could run. Layer 1 exists purely so that code which *does* use the helpers gets fast, precise, zero-lookup attribution instead of falling through to Layer 2's scan.

## 5. Propagation Rules for Ordinary Operations

These rules govern Layers 1 and 2 only (explainability/precision); Layer 0's guarantee does not depend on any of them succeeding.

- **String concat / template literals**: `concatTainted`/the `tainted` tagged-template helper union parent levels (`maxLevel`) and sources, registering a derived `TaintRecord`. Raw `+`/untagged template literals bypass Layer 1 silently, but Layer 2's fallback scan still matches the resulting text's exact/near-duplicate content against the registry.
- **`JSON.stringify`/`JSON.parse`**: `taintAwareJSONStringify` walks the object tree, unions leaf taint, registers the serialized form as derived — but since `JSON.stringify` only escapes, never rewrites, string content, Layer 2 fingerprinting still matches embedded original substrings even when the helper isn't used. `JSON.parse` produces a fresh untainted object at the JS level (Layer 1 fully lost); Layer 2 catches it because the parsed leaves are byte-identical or near-identical to already-registered text.
- **Object spread / array map / filter**: `spreadTainted`/`mapTainted` re-register outputs whose value hash is unchanged as continuing the same record (identity fast path); outputs that differ are re-fingerprinted and fuzzy-matched. Raw spread/map bypass Layer 1 (a documented ergonomic gap) but are still caught by the Layer 2 fallback since spread/map only change shape, not the leaf text.
- **Numbers/booleans/enums extracted from tainted text**: cannot carry a useful fingerprint (nothing to hash usefully). These can only be covered by Layer 0 (scope watermark) or explicit `DERIVED_UNTRUSTED`-tier extraction — this is precisely why boolean/enum decision-laundering is closed by the watermark rather than by fingerprinting (§3.3, §10).
- **Fallback path, always runs**: `scanArgsForTaint(args)` executes before every tool dispatch regardless of whether any helper was used upstream — this is what makes propagation non-manual: even code that never touches a broker helper is still scanned at the one moment that matters, immediately before a real side effect.

## 6. Surviving LLM Summarization/Rewrite — The Load-Bearing Mechanism

This is the mechanism the design is judged hardest on, so it is stated in full, twice: once as the *default* (no sanctioned path used) and once as the *sanctioned* quarantine path.

### 6.1 Default: the watermark gates regardless of what the model writes

When a source tool (`isSource: true`) returns, `ToolCallBroker.call()`:

1. Captures the result, computes its fingerprint, and registers a `TaintRecord` at `level: RAW_UNTRUSTED`.
2. **Atomically, in the same step**, raises the active scope's watermark to `maxLevel(current, RAW_UNTRUSTED)` and appends a `ProvenanceTag`.
3. Only then returns the (optionally wrapped) result to the caller for the model to read.

Every subsequent privileged-sink call in that scope is checked against `scope.watermark.level`, not against the literal content of its own arguments. So when the model later emits a tool call whose arguments are its own hand-written summary, paraphrase, translation, or re-encoding of that content — with zero literal overlap with the source — the sink check still sees `RAW_UNTRUSTED`, because that is what the scope *is*, independent of what the model chose to write. "Please summarize this page and then act on the summary" is caught by construction: the gate never depended on recognizing the summary's content in the first place. The same reasoning closes decision-laundering: a tool call whose arguments are entirely clean strings/booleans, but which was authored in a scope where untrusted content is live, is still gated, because gating never inspected those arguments for tainted text to begin with.

### 6.2 The sanctioned path: `broker.summarize()` / quarantine extraction

Blanket gating of every post-exposure privileged call is a real usability tax (§10). The escape valve — mirroring CaMeL's quarantined Q-LLM — is a single sanctioned tool, `broker.summarize(text, opts)`. It is not policy-gated the way a registered `ToolExecutor` sink is (it has no `sinkClass` to gate on), but it is fully auditable: every branch — both rejections and the success path — emits an `AuditEvent` under the synthetic tool name `__tttb_summarize` (see §4.1's audit-completeness implementation note), so nothing about its use is invisible to whatever is watching `auditSink`:

1. Requires the input to be a registry-known string (a live `TaintedValue`, or a `taintRecordId` the caller passes) — not arbitrary text the agent retyped from memory. This closes the trivial "just retype it as a fresh string and call summarize on that" loophole, though not fully (see §10).
2. Runs the condensation as a **separate, capability-less LLM invocation**, supplied by the integrator (`QuarantineImpl`) — no tool access, no conversation history beyond the input text and instructions — optionally constrained to a caller-supplied schema (enum/bounded/typed fields shrink both the injection surface of the output and the value the operator has to trust).
3. **The broker's own code — not the summarizing LLM — unconditionally registers the output as a new `TaintRecord` with `derivedFrom: [sourceRecordId]`.** This edge cannot be suppressed or spoofed even if the quarantine call itself is prompt-injected, because the registration happens after the LLM call returns, in broker-controlled code.
4. **Raises the scope watermark to `maxLevel(current, DERIVED_UNTRUSTED)`** — never all the way back to `CLEAN`. The quarantine path buys a lower tier, not a clean bill of health.

**Cost, stated plainly**: every large/sensitive tool result now costs one extra LLM round trip to legally condense; a schema-constrained `summarize()` call limits what the agent can say about quarantined content (typed extraction, not free riffing) in exchange for exact rather than fuzzy provenance at exactly the step where fuzzy matching is weakest. Skipping the sanctioned path does not buy a clean result — the scope simply stays at `RAW_UNTRUSTED` and every non-`NONE`-class sink is gated at the stricter tier, so the incentive design rewards routing through quarantine rather than punishing it as extra friction with no payoff.

**Implementation note — landing at `DERIVED_UNTRUSTED`, not `RAW_UNTRUSTED`.** The watermark is monotonic (§4.1): once it reaches `RAW_UNTRUSTED`, no later `summarize()` call can bring it back down to `DERIVED_UNTRUSTED`. So a composite tool meant to demonstrate the quarantine path's lighter tier — "fetch this page, then only ever hand the agent a quarantined summary of it" — must not itself be a broker-registered `isSource: true` tool whose raw result is returned to the caller (that would raise the watermark to `RAW_UNTRUSTED` before `summarize()` ever runs, per §6.1). Instead, such a tool fetches raw content as an internal implementation detail, registers it directly via `broker.registry.register(text, provenance, 'RAW_UNTRUSTED', sensitivity)` (which creates a `TaintRecord` for `summarize()` to reference but — unlike `applyPostExecutionEffects` in `broker.ts` — does **not** touch the watermark), and only then calls `broker.summarize()`, whose own effect raises the watermark straight to `DERIVED_UNTRUSTED`. The raw text is registry-known (so `summarize()`'s input-provenance check in §6.2 step 1 accepts it) without ever having been "returned to the caller for the model to read" in the sense that matters for §6.1. See `corpus/cases.ts` (`summarize-then-act-write-file`) for a worked example.

**Implementation note — what `summarize()` approximates, and where it stops short.** §6.2 already names the reference point: "mirroring CaMeL's quarantined Q-LLM." The fuller version of that architecture is a genuine two-model split: a **privileged model** that orchestrates and holds tool access but never has untrusted content in its own context at all, and a separate **quarantined model** that reads untrusted content and has no tool access whatsoever, returning only symbolic references (a variable name, a handle) the privileged side can pass through to a tool call without ever reading the value itself. Under that design, the paraphrase step this library's whole §6 is built to survive simply can't reach a sink, structurally — there's no path from "content the quarantined model produced" to "argument a tool call executes," because the privileged model that issues tool calls literally never has that content in its own context to put there.

`broker.summarize()` is a real but narrower approximation of the same idea, not that architecture: it's a single quarantined, capability-less LLM call, but its **output still returns to the caller as an ordinary string** the agent's own context can hold and later reference in a tool-call argument — which is exactly why `summarize()`'s output still needs a watermark raise (`DERIVED_UNTRUSTED`, never all the way to `CLEAN`) and provenance-linked policy gating, rather than being structurally incapable of reaching a sink the way the full split's symbolic-reference-only design would be. This library doesn't implement the full privileged/quarantined split because it isn't a decision a tool-call broker can make on an integrator's behalf — it's an orchestration-pattern choice (which model calls which, how a symbolic reference gets threaded through a real tool-call's argument schema) that belongs to whoever is building the agent loop this broker sits inside of, not to the broker itself. `summarize()` is the sanctioned tool for an integrator who wants to move toward that architecture without having to build the quarantine/provenance machinery themselves; it is deliberately not a claim that this library *is* that architecture.

One specific piece of the full split's guarantee — "the quarantined model has no tool access whatsoever" — **is** actually enforced here, though, not merely conventional: `QuarantineImpl` (the Q-LLM callback an integrator supplies to `summarize()`) cannot itself call `broker.call()` on this broker instance. This wasn't purpose-built for this — it falls directly out of the reentrancy guard `summarize()`'s own serialization wrapper already needed for lock-safety (the fix for GAPS.md #17): the guard's `AsyncLocalStorage` context is active for the callback's entire execution window, whether `summarize()` was invoked top-level or nested inside a composite tool's own `execute()` (§6.2's fetch-and-quarantine pattern, `mayCallSummarize: true`) — so a `QuarantineImpl` attempting `broker.call(...)` hits the exact same `ReentrantCallError` a tool's `execute()` re-entering the broker would, before the attempted call's tool ever runs. `test/broker.spec.ts` (`"a quarantineImpl (Q-LLM) callback cannot call broker.call()"`, both the top-level and composite-tool-nested variants) proves this rather than just asserting it. This closes the "no tool access" half of the full split's guarantee, not the "output is a symbolic reference, never a directly-usable string" half — that half remains genuinely unimplemented, as described above; a `QuarantineImpl` can still, entirely legitimately, return a string the agent later builds a tool-call argument from.

**Implementation note — counterfactual argument diffing: the comparison primitive is shipped, the re-run itself is not, and cannot be.** GAPS.md #15's overclaiming disclaimer names the actual limit precisely: this design gates on exposure, a sound proxy for influence, not proof of it — "was untrusted content live in scope" and "did the model's reasoning actually depend on it" are different questions, and only the first one is answered here. One way to close that specific gap, at least partially: when a privileged call is proposed after untrusted content entered scope, re-run the same step with the tainted content excised (or replaced with an inert placeholder) and diff the resulting proposed arguments against what was actually proposed. A difference is direct evidence the untrusted content shaped the call — exactly the signal a paraphrase or heavy rewrite destroys for Layer 2's fingerprint matching (§4.2, GAPS.md #8), recovered a different way.

The re-run half of this is deliberately **not** implemented, and not merely "not gotten to yet": it requires a second live model call per gated decision (real cost, on every privileged call, not just source reads the way `summarize()`'s cost is) that only the integrator's own agent loop can make — this library has no model access at all (the same "TTTB has no opinion on which model you use" stance `quarantine.ts` already takes for `summarize()`). The diffing half is a different story: `taint/counterfactual-diff.ts`'s `diffProposedArgs(actual, counterfactual)` is a shipped, tested, pure utility an integrator calls AFTER doing their own re-run, so nobody has to hand-write the tree-walking/path-tracking machinery themselves. It walks arbitrary JSON-safe argument trees structurally — objects, arrays, primitives, with `Date`/`RegExp` compared by content and any other non-plain value (`Map`, `Set`, a class instance) by reference rather than silently misrepresented via naive key-enumeration — returning one `ArgDiff` per point of divergence, path-tagged with the same dotted/bracketed convention `TaintMatch.argPath` uses (§4.2), so a diff and a fingerprint match can be cross-referenced directly. This closes the "diff the arguments doesn't trivially generalize to non-textual/structured tool schemas" limit named in an earlier draft of this note. It does **not**, and cannot, close the other two: the two calls' outputs still aren't guaranteed to differ only because of the excised content (ordinary model nondeterminism can produce a spurious diff — mitigating this, e.g. via temperature=0 or majority-voting across several counterfactual re-runs, stays the integrator's problem, not something a pure comparison function can help with), and the absence of a diff is not proof of no influence. Diffing is genuinely just the easy half of this research direction; producing a trustworthy counterfactual to diff against remains out of scope for this library to build and ship as a default mechanism.

## 7. Sink & Policy Model

### 7.1 Sink declaration

```typescript
type SinkClass = 'EXEC' | 'MUTATE' | 'EXFIL' | 'NONE';
type SinkCapability =
  | 'exec:shell' | 'exec:code'                                          // -> EXEC
  | 'write:fs' | 'write:external-account' | 'finance:purchase'
  | 'irreversible:other'                                                // -> MUTATE
  | 'net:outbound' | 'net:email' | 'net:api-call' | 'net:post-message'; // -> EXFIL
```

Every `ToolExecutor` declares `capabilities: SinkCapability[]` (empty ⇒ `NONE`) and `readsPrivateData?: {categories: string[]} | false`. A tool with any non-empty `capabilities` is a sink; one with `readsPrivateData` sets `scope.watermark.privateDataSeen = true` on any call, independent of that call's own taint.

### 7.2 Default policy matrix

`privateDataSeen` is an **escalator**, never a **gate** — this is the fix to the soundness hole both source proposals shared.

| Scope watermark | EXEC sink | MUTATE sink | EXFIL sink |
|---|---|---|---|
| `RAW_UNTRUSTED` | **BLOCK**, unconditionally | `REQUIRE_APPROVAL`; escalates to `BLOCK` if `privateDataSeen` | `REQUIRE_APPROVAL`, unconditionally; escalates to `BLOCK` if `privateDataSeen` (full trifecta) |
| `DERIVED_UNTRUSTED` | `REQUIRE_APPROVAL`, unconditionally (never gated only by the trifecta) | `REQUIRE_APPROVAL` if `privateDataSeen`, else `ALLOW_WITH_WARNING` | `REQUIRE_APPROVAL` if `privateDataSeen` (full trifecta), else `ALLOW_WITH_WARNING` |
| `CLEAN` | ALLOW (logged) | ALLOW (logged) | ALLOW (logged) |

Independent of the table: if `TaintContext.argFingerprintFloor` (Layer 2) reports a live exact/high-confidence match to an untrusted source, the decision is floored at `REQUIRE_APPROVAL` even if the table above would allow it (e.g. a turn-scoped watermark reset while a fingerprint chain still ties this argument to a prior-session untrusted result) — this only ever tightens a verdict, never loosens one.

`QUARANTINE_AND_RETRY` is a defined action in the `PolicyDecision` union (`src/types.ts`), reachable by any custom `PolicyFn` and fully supported by the broker's decision handling (`src/broker.ts`) — surfacing a suggested rewrite ("re-run the source read through `summarize()`, then retry") to whatever handles the verdict, never auto-executed, since unconditional auto-retry-through-quarantine would itself be an attacker-influenceable control-flow decision (`broker.ts`'s `finalizeGated()` treats it exactly like `BLOCK`: never executed, always audited, always surfaced via `ToolCallBlockedError`). The shipped `defaultPolicy` (`src/policy/default-policy.ts`) now constructs this verdict for real, as a final pass run AFTER the table above and the Layer-2 tightening block: whenever the decision the rest of this section would otherwise produce is `BLOCK` or `REQUIRE_APPROVAL` **and** `TaintContext.matchedRecords` names a specifically identifiable untrusted source — an `'exact'` fingerprint match (unambiguous by construction), or a `'simhash'`/`'shingle'` fuzzy match scoring at or above a deliberately conservative bar (`QUARANTINE_MIN_FUZZY_SCORE`, well above `lookupFuzzy()`'s own default `overlapMin`) — `QUARANTINE_AND_RETRY` REPLACES that verdict rather than being offered alongside it. A bare watermark taint with no such match (`matchedRecords` empty, or every entry too weak/ambiguous — a `'wrapper'` or `'quarantine-derived'` match never counts, see `bestQuarantineCandidate()`'s own doc comment) leaves the ordinary `BLOCK`/`REQUIRE_APPROVAL` verdict untouched: there is nothing concrete to suggest quarantining. `suggestedSchemaId` is deliberately left unset by `defaultPolicy` in every case — this library has no schema-registry concept for a policy to name a schema by id (see that field's own doc comment in `types.ts`) — the entire actionable suggestion, including which source to re-run, lives in `reason` instead. See `test/policy.spec.ts` for the unit-level trigger/non-trigger matrix and `corpus/cases.ts`'s `quarantine-and-retry-offered` cases for an end-to-end demonstration through the real broker.

### 7.3 Decision function

```typescript
type PolicyFn = (call: ToolCall, taint: TaintContext) => Promise<PolicyDecision> | PolicyDecision;
```

`TaintContext` carries `{matchedRecords, scopeLevel, argFingerprintFloor, privateDataSeen, sinkClass}`. The shipped default implements the table above; it is a plain function and fully overridable per deployment. `ToolCallBroker.call()` is the **only** path from the agent loop to `ToolExecutor.execute()`; integrators are told, as a hard requirement, that no other code path may invoke a registered executor directly, since the broker enforces nothing it is bypassed for (see §10).

### 7.4 Outbound-host allowlist (opt-in egress firewall)

Most of §7 gates on *exposure* — the argument content, or lack of it, was never the point (§6.1's whole argument). The one exception is `BrokerOptions.allowedOutboundHosts`: a genuinely content-based check, deliberately, because for the specific case it targets — data actually leaving to a network host — the destination itself is exactly the signal that matters, independent of whether the payload is tainted at all. Most real exfiltration doesn't need `exec:shell`; it needs an EXFIL-class sink and somewhere to send the result. An allowlist closes that off structurally.

When set (a `readonly string[]`, matched exactly and case-insensitively — no subdomain/wildcard semantics — or a predicate function for callers who want that), every `EXFIL`-class call's arguments are scanned (`taint/egress.ts`'s `findOutboundHosts`) for genuine absolute `http(s)` URLs *and* genuine email addresses (extracting the domain from each); if any found hostname isn't allowed, the call is rejected with `DisallowedOutboundHostError` **before** the taint-based policy in §7.2 ever runs — implemented in `broker.ts`'s `dispatch()` alongside the plan-freeze check (§11), not as a `TaintContext` field `defaultPolicy` has to know about, so it applies uniformly regardless of which `PolicyFn` is configured and even to a completely `CLEAN` scope. That last point is deliberate, not an oversight: the whole reason to configure an explicit allowlist is a hard structural boundary — "traffic from this deployment never leaves to a host I haven't approved, full stop" — not another `REQUIRE_APPROVAL` prompt a human can rubber-stamp (GAPS.md #7's fatigue risk). A taint-tightening mechanism, applied only once the scope is already somewhat suspect, would miss exactly the case this is for: an agent (compromised, misconfigured, or just hallucinating a destination) trying to send data out on a scope nothing has tainted yet.

The email-address case matters concretely: a `net:email` sink's recipient carries no `http(s)://` scheme at all, so a URL-only check would leave the entire `net:email` capability structurally unreachable by this allowlist — checking it required extending `findOutboundHosts` past pure URL-scheme detection. That extension is deliberately narrow too, for a reason worth stating precisely: the email-address pattern is *anchored* (the whole string, not a substring, must be shaped like `local-part@domain.tld`), which keeps its false-positive rate low enough to be safe as a default for a hard `BLOCK`-capable check. A more general "this string looks like a bare hostname" pattern was considered and deliberately **not** added for the same reason — it would risk matching an ordinary filename or version string and incorrectly blocking a legitimate call, an acceptable cost for an advisory-only heuristic (like `warnOnLikelyUnmarkedSource`/`warnOnLikelyUnclassifiedSink`) but not for one capable of rejecting a real call outright.

**Deliberately narrow in scope** — see GAPS.md #18 for the full list of what this does and doesn't cover, most importantly: a call whose destination is neither a `http(s)` URL nor an email address (a bare hostname string, a target assembled from several fields) is invisible to this check entirely. It is a targeted egress firewall for the specific, common shape of "the target is a literal URL or email argument," not a general egress-classification mechanism.

**Known limitation — false positives from whole-tree scanning, narrowed via a per-tool declaration.** `findOutboundHosts` has no notion of which argument key actually carries a tool's destination *by default* — it scans every string leaf in the call's argument tree, so a benign field whose value merely *happens* to be, in its entirety, a valid URL or email address (e.g. a chat tool's `text` body that is exactly `"https://internal-wiki.example/kb/42"`) is indistinguishable from a real destination and trips the same unconditional hard `BLOCK` as a genuine disallowed egress target, even though the tool never actually contacts that host (see GAPS.md #18). `findOutboundHosts(args, { destinationKeys })` accepts an optional `destinationKeys: readonly string[]` naming the argument key(s) that actually carry a destination; when supplied, only those keys' subtrees (at any depth) are scanned, eliminating false positives from unrelated fields, while omitting it preserves the original whole-tree scan exactly.

This is now threaded through `BrokerOptions.allowedOutboundHosts` itself, not just reachable by calling `findOutboundHosts` directly. `ToolExecutor` (`src/types.ts`) gained an optional `destinationKeys?: readonly string[]` field — declared on the tool at `register()`/`wrap()` time, the same "travels with the tool, not per-call configuration" shape `isSource`/`trusted`/`readsPrivateData`/`mayCallSummarize` already have, since which argument key names a given tool's destination (a webhook tool's `url`, as opposed to its unrelated `text`/`channel`/`notes` fields) is a fixed property of that tool's own schema. `broker.ts`'s `gateDecision()` — the EXFIL gating call site — now calls `findOutboundHosts(argsSnapshot, { destinationKeys: tool.destinationKeys })` instead of the unscoped `findOutboundHosts(argsSnapshot)` it called before. A tool that leaves `destinationKeys` unset gets the original whole-tree scan exactly as it behaved before this field existed, so this is purely additive: no previously-registered tool's gating behavior changes.

## 9. Corpus Test Harness

A corpus case pairs a scripted call sequence with an expected verdict and expected final watermark state. See `corpus/schema.ts` for the `CorpusCase` type and `corpus/cases.ts` for the fourteen attack classes covered (19 cases total) — the eleven canonical classes from the design panel's synthesis, plus `plan-freeze-unplanned-privileged-action` (added once `declarePlan()`, §11, shipped), `unapproved-egress-host` (added once `allowedOutboundHosts`, §7.4, shipped), and `quarantine-provenance-spoof` (added to exercise `summarize()`'s input-provenance mismatch check, GAPS.md #4, for the first time — a source page registered genuinely, then `summarize()` called with unrelated fabricated text, expecting `QuarantineInputMismatchError`/`BLOCK`) — two of which (`untracked-context-channel` and `cross-turn-latent-influence`) are true, asserted known gaps, not silent misses: the corpus proves the library is honest about them, not that it catches them. `cross-turn-latent-influence` carries a second case pairing the identical attack sequence with `resetScope: 'turn-decay'` instead of plain `'turn'`, showing the mitigation actually changing the outcome (BLOCK instead of the sibling case's ALLOW) rather than merely asserting it in prose. `plan-freeze-unplanned-privileged-action` similarly carries a second, multi-step case (`plan-freeze-multi-step-cursor-advances-then-rejects`) exercising `planCursor` advancing past a legitimately-matched first step — with a `NONE`-sinkClass call interleaved to confirm it never consumes a plan slot — before a second, unplanned privileged action is correctly rejected at cursor 1; every other plan-freeze case (and every other `declarePlan()` call in the repository) uses a single-step plan checked only at cursor 0.

A test runner (`runCorpusCase`, `corpus/schema.ts`) replays `setup` through mock source/sink tools to seed the registry and raise the watermark as real calls would, then replays `actions` in order (routing a `quarantine` step through `broker.summarize()` first, when the case declares one), and asserts the recorded `PolicyDecision` and final watermark state match `expected`. Cases tagged with a known-gap `attackClass` assert the **documented** outcome, not an idealized one — so the corpus doubles as a regression check against silently overclaiming coverage.

**Counterfactual baseline.** "N/M passed" alone doesn't establish that anything was actually at stake for a given case — it could pass by matching a documented expectation for a payload that was never going to do anything even if allowed through. `runUnprotectedCase` (also in `corpus/schema.ts`) answers the falsifiable version of the question directly: replay the same case's `actions` against the same fixtures with no broker mediating the call at all (no `broker.call()`, no watermark, no gating), and report whether the sink call(s) would have executed. `npm run corpus`'s summary line combines the two: of the corpus's non-benign cases, how many would have executed unprotected, and of those, how many the broker's actual decision would have stopped (`BLOCK`, or `REQUIRE_APPROVAL` with no human present, since the corpus harness always denies) versus let through — split further into the one case that's the sanctioned quarantine path's expected `ALLOW_WITH_WARNING` (the argument reaching the sink is already-summarized, not an attack payload, by that point) and the two true known gaps where protection genuinely provides none. `test/corpus.spec.ts` asserts the "would have executed unprotected" half for every case as a real regression test, not something only visible by reading the CLI output.

Deliberately scoped to `actions` only, not `setup`/`quarantine`: those model how untrusted content reaches the agent's context in the first place, which doesn't depend on whether a broker is watching — an unprotected agent still reads the same page, it just has nothing gating what it does with that content next. The counterfactual is specifically about whether the *sink* call would have gone through.

## 10. Known Gaps & Non-Goals

This library does not achieve soundness in the information-flow-control sense — it achieves a conservative, structural approximation with named, honest limits. See `GAPS.md` for the full, specific enumeration. The single most important non-goal to state plainly: **this design gates on "was untrusted content live in this scope's tracked context," which is a sound, conservative proxy for "did the model act on it," not proof of causal influence** — every claim in this document about "catching summarize-then-act" should be read against that proxy, not as evidence of true interpretability into the model's reasoning.

## 11. Appendix: Optional Strict Mode (Plan-Freeze)

For deployments wanting CaMeL-level control-flow protection (untrusted data cannot introduce a *new* privileged call shape, not just supply values to an existing one), TTTB optionally supports `broker.declarePlan(steps: PlanStep[])`: an ordered list of tool-identity commitments made before any untrusted read (v1 matches on tool identity only — matching on argument shape too is a possible future enhancement, not implemented). Once the scope's watermark leaves `CLEAN`, an incoming **privileged** call (non-`NONE` sinkClass) whose tool does not match the next committed step is rejected with `UnplannedPrivilegedActionError`, and the plan's cursor only ever advances on a step that *did* match — a `NONE`-sink call (including an ordinary source/read-only tool like `fetch_url`) is never gated by policy in the first place and is correspondingly invisible to the plan: it neither needs to appear as a step nor consumes one, and runs freely interleaved with the planned privileged steps. This check is strictly additive: it runs *in addition to*, never *instead of*, the normal policy decision in §7 — a call that matches the plan can still be `BLOCK`ed by policy, and matching the plan is never itself a reason to skip that check. `declarePlan()` throws `PlanNotDeclarableError` if called after the scope has already left `CLEAN`, since committing to a plan retroactively would let the very content the plan is meant to constrain help shape the plan itself.

This is **not** the default — committing to full call shape and count before seeing the data that determines how many calls are needed is a poor fit for standard single-step ReAct-style tool calling and imposes a real practicality cost — but it is available as an additive, stricter layer for high-stakes autonomous agents that can tolerate it.

**A declared plan survives `serializeBrokerState()`/`restoreBrokerState()` (§4.1's persistence note, GAPS.md #12)**, including the exact cursor position it was at when exported. `SerializedBrokerState` (`persistence.ts`) carries two new optional fields alongside the watermark/registry it already had — `plan: PlanStep[]` and `planCursor: number` — plus an explicit `schemaVersion` marker so this and any future wire-format extension has something to actually version against; a `SerializedBrokerState` from before this feature shipped simply has none of the three fields, and `restoreBrokerState()` treats their absence as "no plan was ever exported," a safe no-op that restores watermark/registry exactly as it always did. "Resuming" a plan mid-sequence means exactly what it sounds like: `serializeBrokerState()` reads the exporting broker's live plan state via the new `ToolCallBroker.planState` accessor and writes out both the full step list AND the current cursor, and `restoreBrokerState()`'s returned `initialPlan` seeds a freshly-constructed broker with that SAME cursor position (not step 0) via a new `BrokerOptions.initialPlan` construction-time option — `createBroker({ ...restoreBrokerState(state) })` resumes exactly where the exporting broker left off.

This deliberately bypasses `declarePlan()`'s own `CLEAN`-only guard — `declarePlan()` itself is completely untouched and still throws `PlanNotDeclarableError` once the scope has left `CLEAN` (exactly the state a restored non-`CLEAN` watermark is usually in), so re-declaring a plan by calling `declarePlan()` on a restored broker remains just as impossible as before. `BrokerOptions.initialPlan` is a separate, construction-time-only path precisely because restoring an already-legitimately-declared plan is a different trust question than the one `declarePlan()`'s guard protects against: that guard exists to stop untrusted content ALREADY LIVE IN THIS SCOPE, RIGHT NOW, from shaping a plan being declared now, whereas restoring here carries forward a commitment that was made validly on the ORIGINAL broker, while ITS scope was still `CLEAN`, before that broker's own exposure ever happened.

**Safety property.** Restoring a plan — even a fully adversarially-tampered `SerializedBrokerState.plan` from a corrupted or hand-edited `session.json`, since `SerializedBrokerState` is externally-sourced input per `InvalidBrokerStateError`'s own validation boundary — can only ever make FUTURE privileged calls MORE restrictive, never less. This falls straight out of plan-freeze's own "strictly additive" property stated above: a call whose tool matches the (possibly bogus) next plan step still has to clear the ordinary policy/outbound-allowlist decision exactly as if no plan existed at all, and a call that does NOT match is rejected as unplanned regardless of what a tampered plan "intended." There is no shape of plan content that grants a call any permission it would not otherwise have had — the worst a tampered plan can do is cause spurious `UnplannedPrivilegedActionError` over-blocking of a call the ordinary policy would have allowed, an availability cost, never a soundness one. `validateSerializedBrokerState()` still rejects a malformed `plan`/`planCursor` SHAPE up front (not an array of plan-step-shaped objects, or a cursor out of `[0, plan.length]`) with `InvalidBrokerStateError`, the same "fail loud at the trust boundary" reasoning already applied to `watermark.level` — but that check is about shape, not content, since per the safety property above no plan content can turn into a policy bypass. `test/persistence.spec.ts` exercises the full round trip (including a mid-plan cursor and the exact before/after `UnplannedPrivilegedActionError` comparison this section used to describe as broken) and a deliberately tampered plan, rather than leaving any of this as an unverified claim.
