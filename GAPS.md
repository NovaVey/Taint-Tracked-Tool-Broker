# GAPS.md — Known Limitations of the Taint-Tracked Tool Broker

This library gates privileged tool calls on a conservative, structural proxy: **"was untrusted content live in this scope's tracked context when this call was made"** — not on "did the model's reasoning actually depend on that content." That proxy is sound and cheap to compute, and it is why the broker survives paraphrase, translation, and decision-laundering (see `DESIGN.md` §6) without needing to interpret the model's reasoning. But it is still a proxy, with real, specific edges where it does not help. This document names them plainly rather than leaving them to be discovered in production.

Every case below has a corresponding entry in the injection corpus (`corpus/cases/`) — the two marked **TRUE KNOWN GAP** are asserted in the corpus as gaps, not silently passing tests.

## 1. Untracked context-injection channels — **TRUE KNOWN GAP**

The watermark is raised only by `ToolCallBroker.call()` observing a tracked tool result or a sanctioned quarantine call. Untrusted content that reaches the model's context any other way — a poisoned MCP/tool/plugin description, an untrusted system-prompt fragment, or content the user pastes directly into a turn — never raises the watermark and is invisible to every downstream check. Integrators must call the exposed `markContextExposure()` escape hook for any such channel; the library cannot discover it automatically. `markContextExposure()` now accepts an optional `text`, registering the exposed content into the Layer 2 fingerprint registry (the same register-then-raise pattern an ordinary source-tool call gets) instead of leaving it permanently invisible to fuzzy matching — closes the "how would I even do this well" half, not the "will the integrator remember to call it" half.

One thing narrows this gap's most likely real-world trigger — an ordinary tool that should have been `isSource: true` and simply wasn't — without fully closing it, since it can't discover a channel the library truly never sees at all: `createBroker({ warnOnLikelyUnmarkedSource })` is an opt-in, purely advisory heuristic that flags (via `AuditEvent`, never by touching the watermark or any verdict) a `NONE`-sinkClass call not declared `isSource: true` returning a substantial amount of text. It doesn't replace the integrator's own judgment about which channels exist in their stack, and it can't help with a channel that never routes through a registered tool call at all (a poisoned MCP tool description, an untrusted system-prompt fragment) — those still need an explicit `markContextExposure()` call at the point the integrator's own code observes them.

`examples/mcp-integration.ts` (`npm run example:mcp`) works through this gap's own canonical example concretely: which MCP protocol surface (`tools/call`, `resources/read`, `tools/list`) maps to which mechanism (source wrapping vs. `markContextExposure()`), plus a reusable tool-description-fingerprinting guard that detects a server rewriting a tool's description between two `tools/list` calls (a "rug pull") and calls `markContextExposure()` automatically at the moment of the change. The guard only detects that a description *changed* — deliberately, not whether any one description is malicious, for the same reason GAPS.md #14 keeps its distance from content-matching heuristics.

`examples/mcp-sdk-integration.ts` (`npm run example:mcp-sdk`) runs the identical pattern against a genuine `@modelcontextprotocol/sdk` `McpServer` and `Client` — connected via the SDK's own `InMemoryTransport.createLinkedPair()` so it stays offline, but doing real JSON-RPC request/response and a real server-side `RegisteredTool.update()` rug pull, not a mock. It exists to confirm the wiring pattern above holds against the actual current SDK shapes, not just a hand-rolled stand-in for them.

## 2. Cross-turn / cross-session latent influence — **TRUE KNOWN GAP**

Under `resetScope: 'turn'` (the lower-friction mode), content read in turn N that shapes model behavior in turn N+2 with no new tool result in between is invisible once the turn boundary clears the watermark. `resetScope: 'session'` closes this but pays a larger blanket-gating cost across the whole session; this is a deliberate, named trade the operator must choose, not something the library resolves for them.

`resetScope: 'turn-decay'` (with a required `turnDecayWindow`) is a third, bounded middle ground: instead of clearing at the very next turn boundary, the watermark persists across `turnDecayWindow` consecutive turns with no NEW exposure before clearing, and a fresh exposure during that window restarts the countdown from itself rather than the original exposure. `turnDecayWindow: 1` is exactly equivalent to `'turn'` — it generalizes 'turn' mode, it doesn't replace it. This narrows the gap's window to a chosen, quantified size; it does **not** close it — content read in turn N can still shape behavior in turn N+`turnDecayWindow` with no new exposure in between, the same shape of gap, just bounded instead of unbounded-at-one-turn. `resetScope: 'session'` remains the only choice that closes this gap outright. See DESIGN.md's implementation note and the `turn-decay-narrows-cross-turn-gap` corpus case, which runs the identical attack sequence as the known-gap case above under `'turn-decay'` and shows the outcome actually changing (`BLOCK` instead of `ALLOW`) rather than merely asserting it.

## 3. Blanket post-exposure friction is the core usability cost, not a side effect

Once `RAW_UNTRUSTED` (or, for `EXEC` sinks, even `DERIVED_UNTRUSTED`) is set in a scope, every privileged call in that scope is gated regardless of whether it has any real relationship to the untrusted content that triggered the watermark. Long sessions that read one untrusted page early can face approval friction for many unrelated later actions. The only mitigations are disciplined use of the `summarize()`/quarantine path and narrower scoping, both of which are adoption costs, not automatic fixes.

## 4. The quarantine path only bounds risk if the extraction schema is actually narrow

A `summarize()` call with an unconstrained free-text field lets an injected payload ride through largely intact, and `DERIVED_UNTRUSTED` policy is deliberately lighter than `RAW_UNTRUSTED` for `MUTATE`/`EXFIL` sinks — so a wide-open schema quietly reintroduces much of the risk the tier distinction exists to reduce. Narrow, typed schemas are the safety property; this is a documented usage discipline, not something the type system enforces.

`summarize()`'s own input-provenance check (§6.2 step 1) requires `text` to be substantially derived from the claimed `sourceTaintRecordId` — a length-ratio cap plus an asymmetric shingle-coverage check (`quarantine.ts`), not a spoofing-proof verification. An adversarial input crafted to sit just inside both thresholds (e.g. a large genuine quote from the source padded with a modest amount of fabricated content, still under the length cap) can still pass. This closed a real, reproduced bypass found during review — a huge fabricated payload could ride through by borrowing a single shingle from a tiny source, because the original check used a symmetric overlap coefficient dominated by whichever side was smaller — but "closed the reproduced exploit" is not the same claim as "unspoofable."

The injection corpus now has direct regression coverage for this check, previously untested end-to-end: `corpus/cases.ts`'s `quarantine-provenance-spoof-fabricated-text` case (attack class `quarantine-provenance-spoof`) registers a genuine source page and calls `summarize()` with unrelated, fabricated text, asserting the check correctly throws `QuarantineInputMismatchError` and the call reports `BLOCK`. Previously both corpus quarantine cases passed byte-identical text through `summarize()`, so `exactHash(text) === sourceRecord.id` was always true and this entire branch went unexercised by the corpus.

## 5. Implicit/covert channels through an already-approved option set

If a sink accepts a choice among a small number of pre-approved values (e.g. five hardcoded email templates) and only the choice itself is influenced by untrusted content, the watermark still gates the call correctly — but a design that allowlists specific argument values as always-safe (a common performance/usability optimization operators may add) can reopen a narrow signaling channel this library does not close.

## 6. Steganographic / timing covert channels on already-permitted traffic

Message timing, casing/whitespace patterns in an allowed response, or selection among allowed low-stakes options are out of scope for any taint-tracking design, including this one. No content- or context-level mechanism stops a sufficiently patient covert channel riding on approved traffic.

## 7. Human-approval fatigue and social engineering are unsolved human-factors problems

A conservative default policy that frequently returns `REQUIRE_APPROVAL` after any untrusted exposure creates real pressure toward reflexive click-approval — and the same untrusted content that triggers the approval can also shape the surrounding context an approver sees. The broker surfaces the decision point, the taint sources, and the raw matched content, but cannot force genuine scrutiny.

## 8. Fingerprint (Layer 2) coverage has real, expected false negatives

Heavy paraphrase, cross-language translation, and encoding transforms (base64, hex, homoglyphs, zero-width characters) defeat exact-hash and shingle/simhash matching. This no longer breaks soundness in this design (the watermark still gates the sink regardless), but it does mean the *explanation* attached to a block/require-approval verdict degrades from a precise "this argument literally contains text from source X" to a coarse "this scope is tainted, source unknown" — an audit-quality cost, not a safety cost, as long as the content entered through a tracked channel.

A narrower, structural one worth naming directly: `wordShingles()` (`fingerprint.ts`) used to fall back to treating an entire short text (fewer than `SHINGLE_WIDTH` = 5 words) as a single shingle, which meant two near-identical short texts — differing only by word order, or by a single word — scored exactly 0 overlap, a full miss rather than a partial one, for exactly the shortest and most common realistic payloads (a URL, an account number, a short instruction). Fixed: short texts now shingle at the largest narrower width that still yields overlapping windows, restoring partial-overlap detection for short-text reorderings/near-duplicates. Still open, and not fixable without a real storage/indexing cost this library has not paid: a short excerpt narrow enough to still hit that fallback, embedded verbatim inside a MUCH longer document, still shares no shingle string with it, since a shingle is a whole joined n-gram string and the long document is always shingled at the single, wider `SHINGLE_WIDTH` — closing that would need multi-width shingling applied to every registered document, not just short ones, at a cost proportional to how many widths are added (see the fixed-size-sketch tradeoff DESIGN.md's implementation note and `bench/minhash-sketch-tradeoff.ts` already measured and rejected for a related reason).

Two more, since fixed: (1) `exactHash()` hashed text via Node's UTF-8 encoding, which lossily substitutes U+FFFD for any unpaired/lone UTF-16 surrogate code unit before hashing — so two distinct JS strings differing only in *which* invalid lone surrogate they contained (a realistic byproduct of truncating a tool result mid-character, not a purely theoretical input) could hash identically, a real `TaintRecord.id` collision between genuinely different content. Fixed by a narrowly-scoped `escapeLoneSurrogatesForHashing()` pre-processing step, used only inside `exactHash()`, that rewrites each lone surrogate into a distinct deterministic ASCII marker before hashing — a byte-for-byte no-op for every well-formed string (pinned by a dedicated test), so no existing `TaintRecord.id` changes. (2) `normalize()` strips everything outside letters/numbers/whitespace, so any text made *entirely* of punctuation/symbols/emoji (a decorative banner, an all-emoji message) normalized to the empty string, making `wordShingles()` return `[]` and `computeSimhash()` return the fixed sentinel `0n` regardless of actual content — two completely unrelated symbol-only texts registered as a spurious "perfect" simhash match. Fixed by a new `charShingles()` fallback, used only when `normalize()` yields zero words, that shingles over the raw text's own code points instead of returning nothing — restoring genuine content-sensitivity for this case. Neither fix is load-bearing for the Layer 0 safety gate; both only affect Layer 2 attribution/fuzzy-matching precision.

## 9. Fingerprint false positives from coincidental overlap

Benign boilerplate, disclaimers, or common phrasing shared between trusted and untrusted sources can produce spurious Layer-2 fuzzy matches, adding noisy source attribution to a verdict — though this never independently causes a false `BLOCK`, since Layer 2 can only tighten a verdict the watermark already produced, never originate one on its own for an otherwise-`CLEAN` scope.

## 10. Sink/capability misclassification is the integrator's responsibility, unverified by the library

A tool that actually performs exfiltration (a DNS lookup embedded in an argument, a "read-only" API call with a logging side-channel) but is registered with an empty or wrong `capabilities` array is invisible to every policy check. Likewise a tool wrongly omitting `isSource`/`readsPrivateData` silently breaks watermark-raising or the private-data escalator. `docs/classifying-tools.md` is a checklist and worked examples (a filesystem MCP server, a RAG retrieval tool, a "read-only" API with a logging side channel, a code-interpreter tool) for the less-obvious cases — it reduces how often this goes wrong, it cannot verify a declaration against what a tool's `execute()` actually does.

One thing narrows this gap's most common real-world trigger — an ordinary tool (a `write_file`, a `send_email`, a `delete_row`) whose `capabilities` array was simply left empty by mistake, not a deliberately-deceptive one (which this heuristic cannot catch by construction — see below) — without fully closing it: `createBroker({ warnOnLikelyUnclassifiedSink })` is an opt-in, purely advisory heuristic, mirroring `warnOnLikelyUnmarkedSource` above for the mirror-image gap, that flags (via `AuditEvent` at `register()`/`wrap()` time, never by touching what's registered or any verdict) a `sinkClass: 'NONE'` tool whose name contains a keyword (`write`, `delete`, `exec`, `send`, `purchase`, ... — tunable) that often indicates a mutating/dangerous action. It cannot help with the harder half of this gap this section opens with — a tool that is deceptive on purpose, or one whose real behavior simply doesn't show up in its name (the DNS-lookup-in-an-argument and logging-side-channel examples above) — only `docs/classifying-tools.md`'s own judgment-based checklist addresses those.

Two related fixes since: `ToolExecutor.trusted`'s own inline doc comment (`types.ts`) used to frame it as "deterministic/pure tools may opt out" — misleading, since determinism has nothing to do with whether a tool's CONTENT is attacker-influenceable (a perfectly deterministic function can still pure-functionally echo a caller-supplied or otherwise externally-sourced argument), and `trusted: true` is the single most consequential declaration in this whole trust boundary — it exempts an `isSource` tool from Layer 0 AND Layer 2 entirely, with no error and no audit trail. It now names the actual criterion directly (matching `docs/classifying-tools.md`'s own question 2) and warns against the determinism/purity conflation by name. Separately, `docs/classifying-tools.md` itself — the worked-examples checklist this section and README.md both point to — was missing from `package.json`'s `files` allowlist, so an installed (not cloned) copy of this package could not actually resolve that link; `examples/` had the same gap. Both now ship.

## 11. The broker is only as sound as its position as the sole path to execution

Nothing prevents an integration from calling a registered `ToolExecutor`'s `execute()` directly, or from giving a code-execution sink sandboxed code that itself shells out or makes HTTP requests outside the broker entirely. This must be enforced structurally by the integrator (no direct executor references escape the broker, egress control around any sandbox); the library only mediates calls actually routed through `ToolCallBroker.call()`.

## 12. No *automatic* cross-process, cross-agent, or cross-session taint persistence

Watermark and registry state live in one broker instance's memory by default, and nothing makes a second process or agent discover a first one's state on its own. `createBroker({ initialWatermark, registry })` plus `serializeBrokerState()`/`restoreBrokerState()` (`src/persistence.ts`) now give an integrator a supported, JSON-safe way to export one broker's state and seed another with it across an actual process boundary — see `test/persistence.spec.ts` for a worked round trip. That closes the "how would I even do this" half of the gap; it does not close the "does it happen automatically" half. A sub-agent, a spawned worker, or a different tool ecosystem reading content written to a file/DB by this session still re-enters as unmarked unless *something* — the integrator's own orchestration code — actually calls these helpers and threads the result into the next broker. There is no ambient propagation, and there cannot be one without a shared process or an explicit hand-off: this is still the integrator's responsibility, just no longer one they have to build the (de)serialization for themselves.

A related, more specific gap: a declared plan (`declarePlan()`, DESIGN.md §11) does not survive this export/restore at all — `SerializedBrokerState` carries only the watermark and registry. A broker restored from another's exported state silently loses any plan-freeze protection the original had in effect, and `declarePlan()` can't re-establish one afterward if the restored watermark is already non-`CLEAN` (it requires `CLEAN`). A privileged call that would have been rejected as unplanned on the original broker can succeed on the restored one if the ordinary policy decision alone would have allowed or approved it. See DESIGN.md §11's own note and `test/persistence.spec.ts` for the concrete before/after demonstration.

## 13. Performance and cost are real and ongoing

Every large/sensitive tool result that needs condensing costs one extra LLM round trip through `summarize()` — that cost is structural and this library has no way to reduce it. Fingerprint scanning is no longer a flat ongoing cost, either: `InMemoryTaintRegistry` now indexes fuzzy lookups (LSH-banded simhash buckets + a shingle inverted index, `src/taint/registry.ts`) instead of scanning every stored record on every outgoing call, and accepts an optional `maxEntries` (FIFO eviction by true age — `provenance.capturedAt`, not Map insertion order, so `restore()`-ing an old snapshot into an already-live registry still evicts the actually-oldest record) for long-running sessions that need a memory bound. Neither is free: the index adds bookkeeping on every `register()`, and `maxEntries` is opt-in (unbounded by default) rather than a retention policy this library picks for you — an integrator running a genuinely long-lived session still has to choose a bound and accept that eviction only affects Layer 2 attribution/tightening precision, never the Layer 0 watermark itself (see `registry.ts`'s file header). One concrete consequence worth naming directly: if `maxEntries` evicts the specific record a later `summarize()` call names as its `sourceTaintRecordId`, that call fails loudly with `QuarantineInputUnknownError` (indistinguishable from "that id was never registered at all") rather than succeeding with weaker provenance or silently degrading — a real, if narrow, availability cost of bounding the registry, not a correctness one. Named here as an operational concern with better tooling now available, not one this library can make disappear.

Two more bounds since: `checkStringLeaf()`'s hot path now shares one fingerprint computation between the exact and fuzzy checks (`TaintRegistry.lookupCombined()`, `src/taint/scan.ts`/`src/taint/registry.ts`) instead of hashing the same text twice, and both `lookupFuzzy()` (`FuzzyLookupOpts.maxMatches`, default 20) and `scanArgsForTaint()` (a 50-match tree-wide cap) now bound how many `TaintMatch` entries a single lookup or scan can return — a registry holding many attacker-chosen near-duplicate records could otherwise make a single call return an unboundedly large match list. Both caps are level-priority, not score-priority, so the highest-severity match always survives truncation and `argFingerprintFloor` is never affected — see DESIGN.md's implementation note.

A third, since found by the same kind of adversarial-registry-shape reasoning: those two caps only bound the *returned* match list, not the *candidate* set scored to produce it — a registry containing a large cluster of near-duplicate or coincidentally-shingle-colliding records could make a single LSH band or shingle bucket collect a large fraction of the whole registry, silently degrading `lookupFuzzy()`'s per-call cost back toward the O(registry size) linear scan the indexing exists to avoid, `maxMatches`/the 50-match cap notwithstanding (they only truncate the *output*, after the expensive scoring already ran against every candidate). `InMemoryTaintRegistryOpts.maxFuzzyCandidatesPerLookup` (default 2000) now caps the candidate set itself, before scoring — see `registry.ts`'s doc comment for the same "approximate, never load-bearing" tradeoff this shares with the `simhashMaxDistance`/`overlapMin` thresholds above.

Per-record memory (`fingerprint.shingleHashes`, unbounded per record regardless of `maxEntries`) remains proportional to document length — a fixed-size MinHash sketch was investigated as a bound for this and measured, not just reasoned about, to regress the exact "short excerpt embedded in a large document" detection this library's own corpus tests (up to ~35-79% false-negative rates at realistic document sizes even at a generous sketch size), so it was not shipped. See DESIGN.md's implementation note and `bench/minhash-sketch-tradeoff.ts` for the reproducible numbers.

A different resource-exhaustion shape, in argument SHAPE rather than content: `scanArgsForTaint()`'s mandatory tree walk (`taint/scan.ts`), `findOutboundHosts()`'s egress scan (`taint/egress.ts`), and the standalone `diffProposedArgs()` utility (`taint/counterfactual-diff.ts`) all walked an args tree with a plain recursive function and no depth bound — a sufficiently deep tree (nested objects/arrays forwarded as a tool argument, e.g. a prior tool's own deeply-nested JSON result passed straight through) would recurse until the JS call stack overflowed: an unpredictable-depth `RangeError`, not a clean, documented, catchable failure, and — worse, on the mandatory scan path — one that produced ZERO audit trail, since it happened before `gateDecision()` had a `TaintContext` to audit with. All three now throw `ArgsTooDeepError` at a fixed depth of 500 (comfortably below any realistic JS stack limit, comfortably above any realistic legitimate payload); on the mandatory scan/egress paths, `broker.ts`'s `gateDecision()` catches it specifically and records a `BLOCK` audit event (using the CURRENT scope watermark, since that's still valid — only `matchedRecords`/`argFingerprintFloor` are marked as "scan did not complete") before re-throwing, closing both gaps at once. Note this is a narrower, separate concern from `structuredClone()`'s own pre-existing recursion limit inside `cloneArgsOrThrow()` (GAPS.md #16) — `structuredClone` happens to tolerate somewhat deeper trees before it fails (already converted to `NonCloneableArgsError`, not a raw `RangeError`, so that end of the spectrum was already covered), but there was a real, unprotected window between the two depths where neither guard existed.

`Broker.withLock`'s full-serialization cost (§4.1's concurrency implementation note — no two calls run concurrently through one broker, deliberately accepted there for correctness) is now narrower, not gone: a call that can neither be gated (`sinkClass === 'NONE'`) nor raise/mutate the watermark (not an untrusted source, no `readsPrivateData`) bypasses the lock entirely, since it is provably inert to the state the lock protects. This helps a real, common shape — pure-computation/utility tools with no sink capability — but does **not** help the specific case named above: two independent untrusted-source fetches (e.g. two unrelated web pages in one turn) are both barrier-participating (each could raise the watermark) and still fully serialize against each other, by design, since narrowing that specific case would require reasoning about ordering between concurrent *writers*, not just exempting calls that never touch the shared state at all — a meaningfully higher-risk change than what shipped. See DESIGN.md's implementation note for the full design and the adversarial test suite that backs it.

## 14. Threshold tuning for Layer 2 fuzzy matching is an ongoing, adversarial problem

The same cat-and-mouse dynamic seen in plagiarism-detection and spam-filter fingerprinting applies here. Because it now only affects attribution precision and downgrade eligibility rather than the core block/allow soundness boundary, the blast radius of a badly tuned threshold is smaller than in a fingerprint-only design — but it still needs periodic revisiting against the injection corpus.

## 15. Overclaiming disclaimer

This design gates on "was untrusted content live in this scope's tracked context," which is a sound and conservative proxy for "did the model act on it" — but it is still a proxy. It cannot inspect the model's internal reasoning, so it cannot distinguish a privileged call the untrusted content genuinely influenced from one that happens to occur in the same scope but is entirely unrelated. Every claim of "catching summarize-then-act" in `DESIGN.md` should be read as "catching privileged actions taken while untrusted content was in tracked scope," not as evidence of true causal-influence detection.

One way to actually close this specific gap — re-running a gated call with the tainted content excised and diffing the proposed arguments against what was actually proposed, so a real difference becomes direct evidence of influence — is only half a shipped feature: `diffProposedArgs()` (`src/taint/counterfactual-diff.ts`) is a real, tested comparison utility, but producing the counterfactual to diff against requires a second live model call this library cannot make itself (no model access at all), so that half stays a genuine research direction, not something integrated here. See DESIGN.md §6's "counterfactual argument diffing" implementation note for exactly what's shipped versus what remains out of scope (cost, nondeterminism, and — now closed — no clean generalization to non-textual argument schemas).

## 16. Non-cloneable tool-call arguments

`ToolCallBroker.call()` snapshots `args` (via `structuredClone` by default) so that what a human approves, what gets audited, and what actually executes can't silently diverge if something mutates the object in between (§ "Concurrency and args integrity" in `DESIGN.md`). `structuredClone` can't handle every JS value (functions, most class instances, `WeakMap`/`WeakSet`, etc.). This used to fail *open*: when cloning threw, the broker silently fell back to the original live reference for that call, quietly losing the isolation guarantee it exists to provide. It now fails *loud* instead — a call whose args can't be cloned is rejected outright with `NonCloneableArgsError` rather than dispatched on a shared mutable reference. Tool arguments are expected to be JSON-able in essentially all realistic tool-calling APIs, so this remains a narrow edge case; an integrator with a genuine need for a non-cloneable argument type can supply `createBroker({ cloneArgs })` with their own cloning function (still expected to produce an independent copy — see the option's doc comment) instead of hitting the error. Not enforced by the type system either way — a `ToolExecutor<A>` with a non-cloneable `A` will compile fine and only surface at call time.

`jsonSafeClone` (the opt-in fast `cloneArgs` alternative named above) now detects cyclic plain objects/arrays too, via a `WeakSet`-based ancestor guard (the same pattern `taint/scan.ts` already uses), and throws a clean `TypeError` naming the cycle instead of crashing with an undocumented `RangeError` (stack overflow) on a self-referential value. This matters because `jsonSafeClone` is also exported standalone from `src/index.ts` for direct use outside `broker.ts`'s `cloneArgsOrThrow`/`NonCloneableArgsError` wrapping — a caller using it that way previously got an uncontrolled stack-overflow-style crash rather than this module's own advertised fail-loud, typed-error contract for unsupported input. No public signature change; a value that previously crashed the process now throws a catchable `TypeError`.

## 17. `broker.summarize()` is now serialized against `broker.call()` — fixed, with one named residual risk

`ToolCallBroker.call()` serializes every invocation through `Broker.withLock` specifically so a source call's watermark raise always happens-before a concurrently-dispatched sink call's gating check (DESIGN.md §4.1's concurrency note). `broker.summarize()` raises the watermark through the identical `raiseWatermark()` primitive, gated behind its own `quarantineImpl` LLM round-trip, but used to be a standalone function that never acquired that lock: `Promise.all([broker.summarize(pageText, opts), broker.call('shellExec', args)])` let `shellExec`'s fast, synchronous gating check run and decide against the pre-summarize watermark before `summarize()`'s slower LLM call resolved and raised it. Found by a multi-agent improvement-roadmap review; left deliberately unfixed at the time because the obvious fix (wrap `summarize()` in the same `withLock`) would deadlock the documented fetch-and-quarantine composite-tool pattern (§6.2) the moment `summarize()` is called reentrantly from inside a tool's own `execute()`.

**Now fixed**, via the same reentrancy-aware treatment `call()` already has, extended rather than copy-pasted: `summarize()` now checks whether it is already running inside a call() that HOLDS the lock (raises the watermark inline, already serialized, no new lock needed — this is what avoids the deadlock above) or is genuinely top-level / nested inside a lock-barrier-exempt call (DESIGN.md's "narrowing the lock" note) that never took the lock (acquires the lock itself, exactly like a fresh top-level call would). See DESIGN.md's implementation note and `test/broker.spec.ts`'s "broker.summarize() / broker.call() serialization" suite for the concrete before/after and the deadlock-avoidance regression test.

Fixing this surfaced a second, more subtle interaction with the lock-barrier-exemption feature (item 13's own narrowing): a composite tool whose `execute()` calls `broker.summarize()` internally, if it does any genuine async work (e.g. its own fetch) *before* reaching that call, is not actually protected by `summarize()`'s own lock-awareness — by the time `summarize()` runs, a concurrently-dispatched gated call may already have completed its gating check, because the *outer* exempt call never reserved a lock position in the first place. This can't be detected automatically (the library cannot see into an `execute()` function body), so `ToolExecutor` gained `mayCallSummarize?: boolean`: declaring it `true` excludes a tool from lock-barrier exemption, closing this specific interaction. Leaving it unset/false for a tool that DOES call `summarize()` internally reopens exactly this race for that one tool — the same "integrator declares, library enforces" trust boundary item 10's sink/capability misclassification already rests on, not a new category of risk. `test/broker.spec.ts` asserts both directions directly: a correctly-declared tool is protected, and a misdeclared one is not (documented as the actual, undesirable behavior, not silently accepted as fine).

## 18. Outbound-host allowlist (`allowedOutboundHosts`) scope: what it does and doesn't cover

DESIGN.md §7.4's opt-in egress firewall closes off one real, common attack shape — an EXFIL-class call whose target host is a literal URL or email argument, going to somewhere the deployment never approved — but it is deliberately narrow, and worth naming exactly where it stops:

- **No URL or email argument, no check.** It scans for genuine `http(s)` URLs *and* email addresses (extracting the domain from each) — a `net:email` sink's recipient is checked exactly the same as a `net:outbound` sink's URL, since a bare address carries no scheme at all and was, until this was added, the single most consequential blind spot here. What's still invisible: a bare hostname string with no scheme and no `@` (e.g. a raw `host`/`target` field), or a destination assembled by concatenating several argument fields at runtime. Bare-hostname detection was deliberately **not** added alongside the email case: a generic "this string looks like a hostname" heuristic (unlike an anchored email-address pattern) risks matching an ordinary filename or version string and incorrectly `BLOCK`ing a legitimate call — an unacceptable false-positive cost for a hard gate. An integrator who assumes "allowedOutboundHosts covers all my EXFIL sinks" because it's configured is still wrong the moment one of those sinks expresses its destination as anything other than a URL or an email address.
- **Exact hostname match only, by default.** An array allowlist does not do subdomain or wildcard matching — `"example.com"` does not also permit `"sub.example.com"`. This is deliberately strict (a permissive default here would be the more dangerous mistake), but it means a legitimate use of subdomains needs either every subdomain listed explicitly or a predicate function, and this library cannot verify a supplied predicate matches only what the integrator actually intends.
- **DNS-level and redirect-chain smuggling are out of scope entirely.** A hostname that resolves, via DNS trickery, to an attacker-controlled IP is indistinguishable from a legitimate one at this layer — the check only ever looks at the string in the argument, never performs a real network resolution or follows a request. Likewise, an allowlisted host that itself redirects the request elsewhere (a compromised or attacker-influenced allowed service) is invisible: this library mediates the tool-call *argument*, not the actual HTTP transaction a tool's `execute()` goes on to perform.
- **A channel that never passes through a broker-mediated tool call at all is unreachable, the same way GAPS.md #1 already names.** If the model's own conversational output (not a tool call) contains something a client will auto-fetch or render — a markdown image URL, for instance — the broker never sees it, allowlist or not. This is the outbound-direction analog of #1's untracked-context-injection channels, and has the identical fix: there isn't one at this layer; it has to be handled wherever that output actually reaches a client.
- **Over-detection (false positive): no notion of which argument is the actual destination.** `findOutboundHosts()` scans every string value anywhere in an EXFIL call's argument tree, not just the argument that is actually the call's destination. A benign field whose value happens to be, in its entirety, a valid `http(s)` URL or well-formed email address (e.g. a Slack `text` body that is exactly `"https://internal-wiki.example/kb/42"`) is indistinguishable from a real destination and trips the same unconditional hard `BLOCK` (DESIGN.md §7.4) as a genuine disallowed egress target, even though the tool never actually contacts that host. `findOutboundHosts(args, { destinationKeys: [...] })` now accepts an optional `destinationKeys` list naming the argument key(s) that actually carry a tool's destination; when supplied, only those keys' subtrees are scanned, eliminating false positives from unrelated fields. This is opt-in and not yet wired into `BrokerOptions.allowedOutboundHosts` / `broker.ts`'s own EXFIL gating call site — an integrator who wants it today must call `findOutboundHosts` directly with `destinationKeys`. Without it, the scan remains whole-tree by design, for the same reason bare-hostname detection above was deliberately not added: a generic "looks like a destination" heuristic risks being even riskier than the false positives it would fix.

None of this makes the allowlist not worth using — it closes a real, common shape cleanly, and closes it as a hard structural boundary rather than an approval prompt (#7's fatigue risk). It is not, and was never meant to be, a general egress-classification system.

## 19. One broker instance = one session — not enforced, only documented

Every safety guarantee this library makes — the scope watermark, the Layer 2 fingerprint registry, and `withLock`'s call-ordering serialization (§8) — is per-`Broker`-instance in-memory state. There is no built-in mechanism that stops an integrator from constructing one `Broker` and routing two different, concurrent, unrelated agent sessions' tool calls through it (mistaking `BrokerOptions.sessionId` for a lookup/isolation key rather than what it actually is — a label copied into audit records). Doing so does not fail loudly:

- `withLock` still serializes every `call()` on the shared instance against every other `call()` on it, correctly per §8's own guarantee — but that guarantee was only ever meant to hold *within* one session. Applied across two sessions it just means one session's slow approval wait now blocks the other session's unrelated calls too (an availability bug, not a soundness one on its own).
- Far worse: the watermark and registry are *shared* state. One session reading untrusted content raises the *shared* watermark, which now gates the *other* session's calls too — either uselessly over-restrictive (the other session never went near anything untrusted) or, if that other session's own exposure would otherwise have kept things CLEAN, an integrator who works around the false-positive friction by loosening policy for that instance quietly reopens the very isolation the two sessions needed from each other in the first place.

This is the same category of gap as item 10 (sink/capability misclassification) and item 17's `mayCallSummarize` — a trust boundary the library documents and the integrator is responsible for respecting, not one it can verify from inside `call()` itself (a `Broker` instance has no way to know how many logical sessions its caller intends to route through it). Fixed for this release: `createBroker()` and `BrokerOptions.sessionId` in `broker.ts`, and `ToolCallBroker` in `types.ts`, all now carry prominent doc comments stating the one-instance-one-session rule and why violating it is unsafe rather than merely unconventional. No runtime enforcement is planned — there is no sound way to distinguish "one session reusing its broker across turns, as intended" from "two sessions sharing a broker, by mistake" from inside the library.

## Not yet implemented (tracked, not silent)

**`defaultPolicy` never produces `QUARANTINE_AND_RETRY`.** `QUARANTINE_AND_RETRY` is defined in the `PolicyDecision` union (`src/types.ts`) and handled end-to-end by the broker's decision path (`src/broker.ts`), and any custom `PolicyFn` can construct one, but the shipped `defaultPolicy` (`src/policy/default-policy.ts`) never selects it — its decision matrix (DESIGN.md §7.2) only ever resolves to `ALLOW` / `ALLOW_WITH_WARNING` / `REQUIRE_APPROVAL` / `BLOCK`. DESIGN.md §7.2 previously described `QUARANTINE_AND_RETRY` as an active default-policy behavior (including a "suggested rewrite" surfaced with the verdict); that description has been corrected to describe it as available-but-unused-by-default. Actually wiring up automatic quarantine-and-retry (re-running a tool call against a sanitized/quarantined argument set and surfacing a suggested rewrite) as a real `defaultPolicy` behavior remains unimplemented.

Both items previously listed here — plan-freeze strict mode (`DESIGN.md` §11, `declarePlan()`) and indexed registry storage (item 13 above) — are implemented; see those sections. This heading is kept so a future genuinely-unbuilt feature has a documented place to go, rather than being left to a stale TODO buried in code.
