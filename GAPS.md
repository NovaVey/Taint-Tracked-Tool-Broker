# GAPS.md — Known Limitations of the Taint-Tracked Tool Broker

This library gates privileged tool calls on a conservative, structural proxy: **"was untrusted content live in this scope's tracked context when this call was made"** — not on "did the model's reasoning actually depend on that content." That proxy is sound and cheap to compute, and it is why the broker survives paraphrase, translation, and decision-laundering (see `DESIGN.md` §6) without needing to interpret the model's reasoning. But it is still a proxy, with real, specific edges where it does not help. This document names them plainly rather than leaving them to be discovered in production.

Every case below has a corresponding entry in the injection corpus (`corpus/cases/`) — the two marked **TRUE KNOWN GAP** are asserted in the corpus as gaps, not silently passing tests.

## 1. Untracked context-injection channels — **TRUE KNOWN GAP**

The watermark is raised only by `ToolCallBroker.call()` observing a tracked tool result or a sanctioned quarantine call. Untrusted content that reaches the model's context any other way — a poisoned MCP/tool/plugin description, an untrusted system-prompt fragment, or content the user pastes directly into a turn — never raises the watermark and is invisible to every downstream check. Integrators must call the exposed `markContextExposure()` escape hook for any such channel; the library cannot discover it automatically. `markContextExposure()` now accepts an optional `text`, registering the exposed content into the Layer 2 fingerprint registry (the same register-then-raise pattern an ordinary source-tool call gets) instead of leaving it permanently invisible to fuzzy matching — closes the "how would I even do this well" half, not the "will the integrator remember to call it" half.

One thing narrows this gap's most likely real-world trigger — an ordinary tool that should have been `isSource: true` and simply wasn't — without fully closing it, since it can't discover a channel the library truly never sees at all: `createBroker({ warnOnLikelyUnmarkedSource })` is an opt-in, purely advisory heuristic that flags (via `AuditEvent`, never by touching the watermark or any verdict) a `NONE`-sinkClass call not declared `isSource: true` returning a substantial amount of text. It doesn't replace the integrator's own judgment about which channels exist in their stack, and it can't help with a channel that never routes through a registered tool call at all (a poisoned MCP tool description, an untrusted system-prompt fragment) — those still need an explicit `markContextExposure()` call at the point the integrator's own code observes them.

`examples/mcp-integration.ts` (`npm run example:mcp`) works through this gap's own canonical example concretely: which MCP protocol surface (`tools/call`, `resources/read`, `tools/list`) maps to which mechanism (source wrapping vs. `markContextExposure()`), plus a reusable tool-description-fingerprinting guard that detects a server rewriting a tool's description between two `tools/list` calls (a "rug pull") and calls `markContextExposure()` automatically at the moment of the change. The guard only detects that a description *changed* — deliberately, not whether any one description is malicious, for the same reason GAPS.md #14 keeps its distance from content-matching heuristics.

`examples/mcp-sdk-integration.ts` (`npm run example:mcp-sdk`) runs the identical pattern against a genuine `@modelcontextprotocol/sdk` `McpServer` and `Client` — connected via the SDK's own `InMemoryTransport.createLinkedPair()` so it stays offline, but doing real JSON-RPC request/response and a real server-side `RegisteredTool.update()` rug pull, not a mock. It exists to confirm the wiring pattern above holds against the actual current SDK shapes, not just a hand-rolled stand-in for them.

**A specific narrowing, not a general one.** The MCP tool-descriptor-drift instance of this gap named above now has purpose-built, exported, core-library tooling behind it instead of requiring an integrator to hand-roll their own hashing and comparison logic: `createToolDescriptorGuard()` (`src/tool-descriptor-guard.ts`, re-exported from the package root) is the promoted, generalized form of the guard the two example files above used to each define locally as a byte-for-byte-duplicated `createMcpDescriptionGuard()`/`checkDescriptions()` closure — both now import and dogfood the shared function instead of redefining it. It also closes a real hole the description-only example guard had: it fingerprints a tool's FULL descriptor — `name`, `description`, AND its input/parameter JSON schema when the discovery call provides one, via this library's own `exactHash()`/`toRegistrableText()` (`taint/fingerprint.ts`) — not description text alone, since a tool's declared schema is exactly as attacker-controlled as its description once you're talking to an MCP server, and just as capable of steering a model's behavior through poisoned parameter docs (a schema property's own `description` field, say). The baseline is honestly first-time-this-guard-instance-has-seen-this-tool-name, not a session-start anchor this mechanism has no way to actually provide. On a detected change it calls `broker.markToolDescriptionExposure()` — `ALLOW_WITH_WARNING` plus a taint raise, never a hard deny, the same warn-and-taint shape every other advisory heuristic in this library already uses. This closes exactly one specific, NAMED instance of this gap — the MCP `tools/list` description-and-schema channel — with real, tested, importable tooling (`test/tool-descriptor-guard.spec.ts`); it does not touch this item's BROADER claim. Arbitrary system-prompt fragments, content a user pastes directly into a turn, and any other untracked channel this library cannot see structurally still require an integrator's own explicit `markContextExposure()` call, and the fact this item opens with — the watermark is raised only by `ToolCallBroker.call()` observing a tracked tool result or a sanctioned quarantine call, and any other channel is invisible to it — remains completely true.

## 2. Cross-turn / cross-session latent influence — **TRUE KNOWN GAP**

Under `resetScope: 'turn'` (the lower-friction mode), content read in turn N that shapes model behavior in turn N+2 with no new tool result in between is invisible once the turn boundary clears the watermark. `resetScope: 'session'` closes this but pays a larger blanket-gating cost across the whole session; this is a deliberate, named trade the operator must choose, not something the library resolves for them.

`resetScope: 'turn-decay'` (with a required `turnDecayWindow`) is a third, bounded middle ground: instead of clearing at the very next turn boundary, the watermark persists across `turnDecayWindow` consecutive turns with no NEW exposure before clearing, and a fresh exposure during that window restarts the countdown from itself rather than the original exposure. `turnDecayWindow: 1` is exactly equivalent to `'turn'` — it generalizes 'turn' mode, it doesn't replace it. This narrows the gap's window to a chosen, quantified size; it does **not** close it — content read in turn N can still shape behavior in turn N+`turnDecayWindow` with no new exposure in between, the same shape of gap, just bounded instead of unbounded-at-one-turn. `resetScope: 'session'` remains the only choice that closes this gap outright. See DESIGN.md's implementation note and the `turn-decay-narrows-cross-turn-gap` corpus case, which runs the identical attack sequence as the known-gap case above under `'turn-decay'` and shows the outcome actually changing (`BLOCK` instead of `ALLOW`) rather than merely asserting it.

## 3. Blanket post-exposure friction is the core usability cost, not a side effect

Once `RAW_UNTRUSTED` (or, for `EXEC` sinks, even `DERIVED_UNTRUSTED`) is set in a scope, every privileged call in that scope is gated regardless of whether it has any real relationship to the untrusted content that triggered the watermark. Long sessions that read one untrusted page early can face approval friction for many unrelated later actions. The only mitigations are disciplined use of the `summarize()`/quarantine path and narrower scoping, both of which are adoption costs, not automatic fixes.

## 4. The quarantine path only bounds risk if the extraction schema is actually narrow

A `summarize()` call with an unconstrained free-text field lets an injected payload ride through largely intact, and `DERIVED_UNTRUSTED` policy is deliberately lighter than `RAW_UNTRUSTED` for `MUTATE`/`EXFIL` sinks — so a wide-open schema quietly reintroduces much of the risk the tier distinction exists to reduce. Narrow, typed schemas are the safety property; this is a documented usage discipline, not something the type system enforces.

`summarize()`'s own input-provenance check (§6.2 step 1) requires `text` to be substantially derived from the claimed `sourceTaintRecordId` — a length-ratio cap plus an asymmetric shingle-coverage check (`quarantine.ts`), not a spoofing-proof verification. An adversarial input crafted to sit just inside both thresholds (e.g. a large genuine quote from the source padded with a modest amount of fabricated content, still under the length cap) can still pass. This closed a real, reproduced bypass found during review — a huge fabricated payload could ride through by borrowing a single shingle from a tiny source, because the original check used a symmetric overlap coefficient dominated by whichever side was smaller — but "closed the reproduced exploit" is not the same claim as "unspoofable."

The injection corpus now has direct regression coverage for this check, previously untested end-to-end: `corpus/cases.ts`'s `quarantine-provenance-spoof-fabricated-text` case (attack class `quarantine-provenance-spoof`) registers a genuine source page and calls `summarize()` with unrelated, fabricated text, asserting the check correctly throws `QuarantineInputMismatchError` and the call reports `BLOCK`. Previously both corpus quarantine cases passed byte-identical text through `summarize()`, so `exactHash(text) === sourceRecord.id` was always true and this entire branch went unexercised by the corpus.

The "documented usage discipline, not something the type system enforces" framing above is still accurate for the default, unset case — but is now no longer the only option: `createBroker({ requireQuarantineSchema: true })` is a new opt-in strict mode, additive on top of the default (mirroring `declarePlan()`'s plan-freeze strict mode, DESIGN.md §11), that converts this discipline into an integrator-selectable hard guarantee. When enabled, `broker.summarize()` rejects any call whose `opts.schema` is omitted — throwing `QuarantineSchemaRequiredError`, with a matching `BLOCK` `AuditEvent`, before the Q-LLM is ever invoked and before anything reaches the registry — rather than silently falling back to `opts.schema`'s own default of unconstrained free text. It closes only the "forgot to pass a schema at this call site" failure mode, not the two paragraphs above it: a schema that is technically present but too wide (e.g. `{ parse: (x) => String(x) }`, itself still a valid extraction schema) satisfies this check and is untouched by it, and it says nothing about the input-provenance spoofing risk either paragraph already names. Off by default; a broker constructed without it behaves exactly as before this option existed.

## 5. Implicit/covert channels through an already-approved option set

If a sink accepts a choice among a small number of pre-approved values (e.g. five hardcoded email templates) and only the choice itself is influenced by untrusted content, the watermark still gates the call correctly — but a design that allowlists specific argument values as always-safe (a common performance/usability optimization operators may add) can reopen a narrow signaling channel this library does not close.

## 6. Steganographic / timing covert channels on already-permitted traffic

Message timing, casing/whitespace patterns in an allowed response, or selection among allowed low-stakes options are out of scope for any taint-tracking design, including this one. No content- or context-level mechanism stops a sufficiently patient covert channel riding on approved traffic.

## 7. Human-approval fatigue and social engineering are unsolved human-factors problems

A conservative default policy that frequently returns `REQUIRE_APPROVAL` after any untrusted exposure creates real pressure toward reflexive click-approval — and the same untrusted content that triggers the approval can also shape the surrounding context an approver sees. The broker surfaces the decision point, the taint sources, and the raw matched content, but cannot force genuine scrutiny.

## 8. Fingerprint (Layer 2) coverage has real, expected false negatives

Heavy paraphrase, cross-language translation, and encoding transforms (base64, hex, homoglyphs, zero-width characters) defeat exact-hash and shingle/simhash matching. This no longer breaks soundness in this design (the watermark still gates the sink regardless), but it does mean the *explanation* attached to a block/require-approval verdict degrades from a precise "this argument literally contains text from source X" to a coarse "this scope is tainted, source unknown" — an audit-quality cost, not a safety cost, as long as the content entered through a tracked channel.

A narrower, structural one worth naming directly: `wordShingles()` (`fingerprint.ts`) used to fall back to treating an entire short text (fewer than `SHINGLE_WIDTH` = 5 words) as a single shingle, which meant two near-identical short texts — differing only by word order, or by a single word — scored exactly 0 overlap, a full miss rather than a partial one, for exactly the shortest and most common realistic payloads (a URL, an account number, a short instruction). Fixed: short texts now shingle at the largest narrower width that still yields overlapping windows, restoring partial-overlap detection for short-text reorderings/near-duplicates. Still open, and not fixable without a real storage/indexing cost this library has not paid: a short excerpt narrow enough to still hit that fallback, embedded verbatim inside a MUCH longer document, still shares no shingle string with it, since a shingle is a whole joined n-gram string and the long document is always shingled at the single, wider `SHINGLE_WIDTH` — closing that would need multi-width shingling applied to every registered document, not just short ones, at a cost proportional to how many widths are added (see the fixed-size-sketch tradeoff DESIGN.md's implementation note and `bench/minhash-sketch-tradeoff.ts` already measured and rejected for a related reason).

Two more, since fixed: (1) `exactHash()` hashed text via Node's UTF-8 encoding, which lossily substitutes U+FFFD for any unpaired/lone UTF-16 surrogate code unit before hashing — so two distinct JS strings differing only in *which* invalid lone surrogate they contained (a realistic byproduct of truncating a tool result mid-character, not a purely theoretical input) could hash identically, a real `TaintRecord.id` collision between genuinely different content. Fixed by a narrowly-scoped `escapeLoneSurrogatesForHashing()` pre-processing step, used only inside `exactHash()`, that rewrites each lone surrogate into a distinct deterministic ASCII marker before hashing — a byte-for-byte no-op for every well-formed string (pinned by a dedicated test), so no existing `TaintRecord.id` changes. (2) `normalize()` strips everything outside letters/numbers/whitespace, so any text made *entirely* of punctuation/symbols/emoji (a decorative banner, an all-emoji message) normalized to the empty string, making `wordShingles()` return `[]` and `computeSimhash()` return the fixed sentinel `0n` regardless of actual content — two completely unrelated symbol-only texts registered as a spurious "perfect" simhash match. Fixed by a new `charShingles()` fallback, used only when `normalize()` yields zero words, that shingles over the raw text's own code points instead of returning nothing — restoring genuine content-sensitivity for this case. Neither fix is load-bearing for the Layer 0 safety gate; both only affect Layer 2 attribution/fuzzy-matching precision.

Both of these were found by adversarial review, not the (at-the-time-existing) test suite — a real invariant violated by a Unicode input class nobody had happened to hand-write an example for, the textbook property-based-testing failure mode. `test/fingerprint.property.spec.ts` now sweeps `fc.string()` plus arbitraries deliberately weighted toward exactly these two proven bug classes (explicit lone-surrogate injection; symbol-only/emoji-only/whitespace-only text) through `exactHash()`'s no-collision property and `overlapCoefficient()`'s range/symmetry/self-match/containment properties, so the next bug in this shape doesn't get a multi-day window before its own hand-picked repro exists. `test/json-safe-clone.property.spec.ts` and `test/counterfactual-diff.property.spec.ts` apply the same treatment to those two modules' own invariants over arbitrary generated JSON-safe trees.

## 9. Fingerprint false positives from coincidental overlap

Benign boilerplate, disclaimers, or common phrasing shared between trusted and untrusted sources can produce spurious Layer-2 fuzzy matches, adding noisy source attribution to a verdict — though this never independently causes a false `BLOCK`, since Layer 2 can only tighten a verdict the watermark already produced, never originate one on its own for an otherwise-`CLEAN` scope.

## 10. Sink/capability misclassification is the integrator's responsibility, unverified by the library

A tool that actually performs exfiltration (a DNS lookup embedded in an argument, a "read-only" API call with a logging side-channel) but is registered with an empty or wrong `capabilities` array is invisible to every policy check. Likewise a tool wrongly omitting `isSource`/`readsPrivateData` silently breaks watermark-raising or the private-data escalator. `docs/classifying-tools.md` is a checklist and worked examples (a filesystem MCP server, a RAG retrieval tool, a "read-only" API with a logging side channel, a code-interpreter tool) for the less-obvious cases — it reduces how often this goes wrong, it cannot verify a declaration against what a tool's `execute()` actually does.

One thing narrows this gap's most common real-world trigger — an ordinary tool (a `write_file`, a `send_email`, a `delete_row`) whose `capabilities` array was simply left empty by mistake, not a deliberately-deceptive one (which this heuristic cannot catch by construction — see below) — without fully closing it: `createBroker({ warnOnLikelyUnclassifiedSink })` is an opt-in, purely advisory heuristic, mirroring `warnOnLikelyUnmarkedSource` above for the mirror-image gap, that flags (via `AuditEvent` at `register()`/`wrap()` time, never by touching what's registered or any verdict) a `sinkClass: 'NONE'` tool whose name contains a keyword (`write`, `delete`, `exec`, `send`, `purchase`, ... — tunable) that often indicates a mutating/dangerous action. It cannot help with the harder half of this gap this section opens with — a tool that is deceptive on purpose, or one whose real behavior simply doesn't show up in its name (the DNS-lookup-in-an-argument and logging-side-channel examples above) — only `docs/classifying-tools.md`'s own judgment-based checklist addresses those.

Two related fixes since: `ToolExecutor.trusted`'s own inline doc comment (`types.ts`) used to frame it as "deterministic/pure tools may opt out" — misleading, since determinism has nothing to do with whether a tool's CONTENT is attacker-influenceable (a perfectly deterministic function can still pure-functionally echo a caller-supplied or otherwise externally-sourced argument), and `trusted: true` is the single most consequential declaration in this whole trust boundary — it exempts an `isSource` tool from Layer 0 AND Layer 2 entirely, with no error and no audit trail. It now names the actual criterion directly (matching `docs/classifying-tools.md`'s own question 2) and warns against the determinism/purity conflation by name. Separately, `docs/classifying-tools.md` itself — the worked-examples checklist this section and README.md both point to — was missing from `package.json`'s `files` allowlist, so an installed (not cloned) copy of this package could not actually resolve that link; `examples/` had the same gap. Both now ship.

`warnOnLikelyUnclassifiedSink`'s registration-time keyword match is now also available standalone, decoupled entirely from `createBroker()`/`AuditSink` ceremony: `likelyUnclassifiedSinkKeyword(name, keywords?)` (`src/broker.ts`, re-exported from `src/index.ts`) is the exact same pure match `register()` calls internally, usable directly over a whole tool catalog as a manifest-style pre-publish lint — no broker, no `register()`/`wrap()` call, not even a real `ToolExecutor` object, needed to run it. This narrows (does not close) the same "the library cannot verify a declaration against a tool's real behavior" gap this section opens with, for exactly the same reason the live heuristic already can't: it is still a name-keyword match, still blind to a deliberately-deceptive tool or one whose real behavior doesn't show up in its name at all. It also does not extend to `warnOnLikelyUnmarkedSource` (GAPS.md #1) — that heuristic's signal is a real call's returned-text length, a runtime property no registration-only tooling can substitute for. See `docs/classifying-tools.md`'s "Automating what this checklist can automate" section for the worked pattern and this asymmetry stated explicitly.

## 11. The broker is only as sound as its position as the sole path to execution

Nothing prevents an integration from calling a registered `ToolExecutor`'s `execute()` directly, or from giving a code-execution sink sandboxed code that itself shells out or makes HTTP requests outside the broker entirely. This must be enforced structurally by the integrator (no direct executor references escape the broker, egress control around any sandbox); the library only mediates calls actually routed through `ToolCallBroker.call()`.

## 12. No *automatic* cross-process, cross-agent, or cross-session taint persistence

Watermark and registry state live in one broker instance's memory by default, and nothing makes a second process or agent discover a first one's state on its own. `createBroker({ initialWatermark, registry })` plus `serializeBrokerState()`/`restoreBrokerState()` (`src/persistence.ts`) now give an integrator a supported, JSON-safe way to export one broker's state and seed another with it across an actual process boundary — see `test/persistence.spec.ts` for a worked round trip. That closes the "how would I even do this" half of the gap; it does not close the "does it happen automatically" half. A sub-agent, a spawned worker, or a different tool ecosystem reading content written to a file/DB by this session still re-enters as unmarked unless *something* — the integrator's own orchestration code — actually calls these helpers and threads the result into the next broker. There is no ambient propagation, and there cannot be one without a shared process or an explicit hand-off: this is still the integrator's responsibility, just no longer one they have to build the (de)serialization for themselves.

A related, more specific sub-gap this used to describe as open — now closed: a declared plan (`declarePlan()`, DESIGN.md §11) DOES survive this export/restore, including the exact cursor position it was at when exported. `SerializedBrokerState` now carries `plan`/`planCursor` (both optional, alongside a new `schemaVersion` marker for future wire-format changes) in addition to the watermark and registry; a broker restored from another's exported state resumes any live plan-freeze protection the original had in effect exactly where it left off, not from step 0. The mechanism deliberately bypasses `declarePlan()`'s own `CLEAN`-only guard via a separate, construction-time-only `BrokerOptions.initialPlan` option — `declarePlan()` itself is untouched and still throws `PlanNotDeclarableError` on a non-`CLEAN` scope exactly as before. This is sound rather than a bypass because plan-freeze is strictly additive (DESIGN.md §11): restoring a plan, even a fully adversarially-tampered one (`SerializedBrokerState` is externally-sourced input, same as the rest of `InvalidBrokerStateError`'s validation boundary), can only ever make future privileged calls MORE restrictive, never less — a call matching a (possibly bogus) plan step still has to clear the ordinary policy decision unchanged, and a non-matching call is rejected as unplanned regardless of what the plan "intended." See DESIGN.md §11's own note for the full mechanism and safety-property argument, and `test/persistence.spec.ts` for the concrete round-trip (including a mid-sequence cursor and the exact before/after `UnplannedPrivilegedActionError` comparison this paragraph used to point to as the open gap), the backward-compatibility case (an already-shipped 0.x blob with no `schemaVersion`/`plan` restores unchanged, treated as "no plan"), and a deliberately tampered-plan safety-property test.

A related but distinct production footgun, confirmed and now closed — not about crossing a process boundary at all, so it does not narrow the automatic-propagation gap this section is otherwise about: `AuditEvent.taint.matchedRecords[].record.fingerprint` carries the identical `bigint`/`Uint32Array` fields as an exported `TaintRecord`, but reaches an integrator's `AuditSink` on every gated call regardless of whether they ever call `serializeRegistry()`/`serializeBrokerState()`. The single most obvious `AuditSink`, `record(e) { console.log(JSON.stringify(e)) }`, THROWS the moment a call's arguments fuzzy- or exact-match a previously-registered record — the ordinary case for a real attack, not an edge case. `serializeAuditEvent()` (`src/persistence.ts`) fixes this by reusing the exact same per-record conversion `serializeRegistry()` already uses; see `AuditSink`'s own doc comment (`src/types.ts`), DESIGN.md §4.2's matching implementation note, and `test/audit-json-safety.spec.ts` for a real broker.call() sequence confirming both the raw throw and the fix.

A third, narrower gap this section's first two paragraphs didn't cover at all: neither `serializeBrokerState()` (a whole broker) nor `serializeAuditEvent()` (a whole audit event) was purpose-built for handing off a SINGLE value together with its taint provenance to a boundary that has no broker reference to restore anything into in the first place — a downstream microservice, a database row, a UI a human reviews. `createTaintEnvelope(value, taint)` (`src/envelope.ts`) closes that: it packages `value` with a JSON-safe snapshot of a `TaintContext` (scope level, `privateDataSeen`, matched fingerprint records — reusing the identical `serializeTaintRecord()` conversion the two paragraphs above already rely on — and a one-line human-readable summary), most directly built from `ToolCallBlockedError.taint` after a caught blocked/quarantined call. Deliberately one-way, like `serializeAuditEvent()`: there is no `restoreTaintEnvelope()`, and an envelope is never fed back into `createBroker()` — restoring a broker's actual state across a process boundary remains `serializeBrokerState()`/`restoreBrokerState()`'s job. This does not narrow the "does it happen automatically" half of the gap this section opens with either: an envelope still has to be built and forwarded deliberately by the integrator's own code at the point of a gated decision, same as everything else in this section.

## 13. Performance and cost are real and ongoing

Every large/sensitive tool result that needs condensing costs one extra LLM round trip through `summarize()` — that cost is structural and this library has no way to reduce it. Fingerprint scanning is no longer a flat ongoing cost, either: `InMemoryTaintRegistry` now indexes fuzzy lookups (LSH-banded simhash buckets + a shingle inverted index, `src/taint/registry.ts`) instead of scanning every stored record on every outgoing call, and accepts an optional `maxEntries` (FIFO eviction by true age — `provenance.capturedAt`, not Map insertion order, so `restore()`-ing an old snapshot into an already-live registry still evicts the actually-oldest record) for long-running sessions that need a memory bound. Neither is free: the index adds bookkeeping on every `register()`, and `maxEntries` is opt-in (unbounded by default) rather than a retention policy this library picks for you — an integrator running a genuinely long-lived session still has to choose a bound and accept that eviction only affects Layer 2 attribution/tightening precision, never the Layer 0 watermark itself (see `registry.ts`'s file header). One concrete consequence worth naming directly: if `maxEntries` evicts the specific record a later `summarize()` call names as its `sourceTaintRecordId`, that call fails loudly with `QuarantineInputUnknownError` (indistinguishable from "that id was never registered at all") rather than succeeding with weaker provenance or silently degrading — a real, if narrow, availability cost of bounding the registry, not a correctness one. Named here as an operational concern with better tooling now available, not one this library can make disappear.

Two more bounds since: `checkStringLeaf()`'s hot path now shares one fingerprint computation between the exact and fuzzy checks (`TaintRegistry.lookupCombined()`, `src/taint/scan.ts`/`src/taint/registry.ts`) instead of hashing the same text twice, and both `lookupFuzzy()` (`FuzzyLookupOpts.maxMatches`, default 20) and `scanArgsForTaint()` (a 50-match tree-wide cap) now bound how many `TaintMatch` entries a single lookup or scan can return — a registry holding many attacker-chosen near-duplicate records could otherwise make a single call return an unboundedly large match list. Both caps are level-priority, not score-priority, so the highest-severity match always survives truncation and `argFingerprintFloor` is never affected — see DESIGN.md's implementation note.

A third, since found by the same kind of adversarial-registry-shape reasoning: those two caps only bound the *returned* match list, not the *candidate* set scored to produce it — a registry containing a large cluster of near-duplicate or coincidentally-shingle-colliding records could make a single LSH band or shingle bucket collect a large fraction of the whole registry, silently degrading `lookupFuzzy()`'s per-call cost back toward the O(registry size) linear scan the indexing exists to avoid, `maxMatches`/the 50-match cap notwithstanding (they only truncate the *output*, after the expensive scoring already ran against every candidate). `InMemoryTaintRegistryOpts.maxFuzzyCandidatesPerLookup` (default 2000) now caps the candidate set itself, before scoring — see `registry.ts`'s doc comment for the same "approximate, never load-bearing" tradeoff this shares with the `simhashMaxDistance`/`overlapMin` thresholds above.

Per-record memory (`fingerprint.shingleHashes`, unbounded per record regardless of `maxEntries`) remains proportional to document length — a fixed-size MinHash sketch was investigated as a bound for this and measured, not just reasoned about, to regress the exact "short excerpt embedded in a large document" detection this library's own corpus tests (up to ~35-79% false-negative rates at realistic document sizes even at a generous sketch size), so it was not shipped. See DESIGN.md's implementation note and `bench/minhash-sketch-tradeoff.ts` for the reproducible numbers.

A different resource-exhaustion shape, in argument SHAPE rather than content: `scanArgsForTaint()`'s mandatory tree walk (`taint/scan.ts`), `findOutboundHosts()`'s egress scan (`taint/egress.ts`), and the standalone `diffProposedArgs()` utility (`taint/counterfactual-diff.ts`) all walked an args tree with a plain recursive function and no depth bound — a sufficiently deep tree (nested objects/arrays forwarded as a tool argument, e.g. a prior tool's own deeply-nested JSON result passed straight through) would recurse until the JS call stack overflowed: an unpredictable-depth `RangeError`, not a clean, documented, catchable failure, and — worse, on the mandatory scan path — one that produced ZERO audit trail, since it happened before `gateDecision()` had a `TaintContext` to audit with. All three now throw `ArgsTooDeepError` at a fixed depth of 500 (comfortably below any realistic JS stack limit, comfortably above any realistic legitimate payload); on the mandatory scan/egress paths, `broker.ts`'s `gateDecision()` catches it specifically and records a `BLOCK` audit event (using the CURRENT scope watermark, since that's still valid — only `matchedRecords`/`argFingerprintFloor` are marked as "scan did not complete") before re-throwing, closing both gaps at once. Note this is a narrower, separate concern from `structuredClone()`'s own pre-existing recursion limit inside `cloneArgsOrThrow()` (GAPS.md #16) — `structuredClone` happens to tolerate somewhat deeper trees before it fails (already converted to `NonCloneableArgsError`, not a raw `RangeError`, so that end of the spectrum was already covered), but there was a real, unprotected window between the two depths where neither guard existed.

`Broker.withLock`'s full-serialization cost (§4.1's concurrency implementation note — no two calls run concurrently through one broker, deliberately accepted there for correctness) is now narrower, not gone: a call that can neither be gated (`sinkClass === 'NONE'`) nor raise/mutate the watermark (not an untrusted source, no `readsPrivateData`) bypasses the lock entirely, since it is provably inert to the state the lock protects. This helps a real, common shape — pure-computation/utility tools with no sink capability — but does **not** help the specific case named above: two independent untrusted-source fetches (e.g. two unrelated web pages in one turn) are both barrier-participating (each could raise the watermark) and still fully serialize against each other, by design, since narrowing that specific case would require reasoning about ordering between concurrent *writers*, not just exempting calls that never touch the shared state at all — a meaningfully higher-risk change than what shipped. See DESIGN.md's implementation note for the full design and the adversarial test suite that backs it.

## 14. Threshold tuning for Layer 2 fuzzy matching is an ongoing, adversarial problem

The same cat-and-mouse dynamic seen in plagiarism-detection and spam-filter fingerprinting applies here. Because it now only affects attribution precision and downgrade eligibility rather than the core block/allow soundness boundary, the blast radius of a badly tuned threshold is smaller than in a fingerprint-only design — but it still needs periodic revisiting against the injection corpus.

## 15. Overclaiming disclaimer

This design gates on "was untrusted content live in this scope's tracked context," which is a sound and conservative proxy for "did the model act on it" — but it is still a proxy. It cannot inspect the model's internal reasoning, so it cannot distinguish a privileged call the untrusted content genuinely influenced from one that happens to occur in the same scope but is entirely unrelated. Every claim of "catching summarize-then-act" in `DESIGN.md` should be read as "catching privileged actions taken while untrusted content was in tracked scope," not as evidence of true causal-influence detection.

One way to actually close this specific gap — re-running a gated call with the tainted content excised and diffing the proposed arguments against what was actually proposed, so a real difference becomes direct evidence of influence — is only half a shipped feature: `diffProposedArgs()` (`src/taint/counterfactual-diff.ts`) is a real, tested comparison utility, but producing the counterfactual to diff against requires a second live model call this library cannot make itself (no model access at all), so that half stays a genuine research direction, not something integrated here. See DESIGN.md §6's "counterfactual argument diffing" implementation note for exactly what's shipped versus what remains out of scope (cost, nondeterminism, and — now closed — no clean generalization to non-textual argument schemas).

## 16. Non-cloneable tool-call arguments

`ToolCallBroker.call()` snapshots `args` (via `structuredClone` by default) so that what a human approves, what gets audited, and what actually executes can't silently diverge if something mutates the object in between (§ "Concurrency and args integrity" in `DESIGN.md`). `structuredClone` can't handle every JS value (functions, most class instances, `WeakMap`/`WeakSet`, etc.). This used to fail *open*: when cloning threw, the broker silently fell back to the original live reference for that call, quietly losing the isolation guarantee it exists to provide. It now fails *loud* instead — a call whose args can't be cloned is rejected outright with `NonCloneableArgsError` rather than dispatched on a shared mutable reference. Tool arguments are expected to be JSON-able in essentially all realistic tool-calling APIs, so this remains a narrow edge case; an integrator with a genuine need for a non-cloneable argument type can supply `createBroker({ cloneArgs })` with their own cloning function (still expected to produce an independent copy — see the option's doc comment) instead of hitting the error. Not enforced by the type system either way — a `ToolExecutor<A>` with a non-cloneable `A` will compile fine and only surface at call time.

`jsonSafeClone` (the opt-in fast `cloneArgs` alternative named above) now detects cyclic plain objects/arrays too, via a `WeakSet`-based ancestor guard (the same pattern `taint/scan.ts` already uses), and throws a clean `TypeError` naming the cycle instead of crashing with an undocumented `RangeError` (stack overflow) on a self-referential value. This matters because `jsonSafeClone` is also exported standalone from `src/index.ts` for direct use outside `broker.ts`'s `cloneArgsOrThrow`/`NonCloneableArgsError` wrapping — a caller using it that way previously got an uncontrolled stack-overflow-style crash rather than this module's own advertised fail-loud, typed-error contract for unsupported input. No public signature change; a value that previously crashed the process now throws a catchable `TypeError`.

## 17. `broker.summarize()` is now serialized against `broker.call()` — fixed, with one named residual risk

`ToolCallBroker.call()` serializes every invocation through `Broker.withLock` specifically so a source call's watermark raise always happens-before a concurrently-dispatched sink call's gating check (DESIGN.md §4.1's concurrency note). `broker.summarize()` raises the watermark through the identical `raiseWatermark()` primitive, gated behind its own `quarantineImpl` LLM round-trip, but used to be a standalone function that never acquired that lock: `Promise.all([broker.summarize(pageText, opts), broker.call('shellExec', args)])` let `shellExec`'s fast, synchronous gating check run and decide against the pre-summarize watermark before `summarize()`'s slower LLM call resolved and raised it. Found by a multi-agent improvement-roadmap review; left deliberately unfixed at the time because the obvious fix (wrap `summarize()` in the same `withLock`) would deadlock the documented fetch-and-quarantine composite-tool pattern (§6.2) the moment `summarize()` is called reentrantly from inside a tool's own `execute()`.

**Now fixed**, via the same reentrancy-aware treatment `call()` already has, extended rather than copy-pasted: `summarize()` now checks whether it is already running inside a call() that HOLDS the lock (raises the watermark inline, already serialized, no new lock needed — this is what avoids the deadlock above) or is genuinely top-level / nested inside a lock-barrier-exempt call (DESIGN.md's "narrowing the lock" note) that never took the lock (acquires the lock itself, exactly like a fresh top-level call would). See DESIGN.md's implementation note and `test/broker.spec.ts`'s "broker.summarize() / broker.call() serialization" suite for the concrete before/after and the deadlock-avoidance regression test.

Fixing this surfaced a second, more subtle interaction with the lock-barrier-exemption feature (item 13's own narrowing): a composite tool whose `execute()` calls `broker.summarize()` internally, if it does any genuine async work (e.g. its own fetch) *before* reaching that call, is not actually protected by `summarize()`'s own lock-awareness — by the time `summarize()` runs, a concurrently-dispatched gated call may already have completed its gating check, because the *outer* exempt call never reserved a lock position in the first place. This can't be detected automatically (the library cannot see into an `execute()` function body), so `ToolExecutor` gained `mayCallSummarize?: boolean`: declaring it `true` excludes a tool from lock-barrier exemption, closing this specific interaction. Leaving it unset/false for a tool that DOES call `summarize()` internally reopens exactly this race for that one tool — the same "integrator declares, library enforces" trust boundary item 10's sink/capability misclassification already rests on, not a new category of risk. `test/broker.spec.ts` asserts both directions directly: a correctly-declared tool is protected, and a misdeclared one is not (documented as the actual, undesirable behavior, not silently accepted as fine).

## 18. Outbound-host allowlist (`allowedOutboundHosts`) scope: what it does and doesn't cover

DESIGN.md §7.4's opt-in egress firewall closes off one real, common attack shape — an EXFIL-class call whose target host is a literal URL or email argument, going to somewhere the deployment never approved — but it is deliberately narrow, and worth naming exactly where it stops:

- **No URL or email argument, no check.** It scans for genuine `http(s)` URLs *and* email addresses (extracting the domain from each) — a `net:email` sink's recipient is checked exactly the same as a `net:outbound` sink's URL, since a bare address carries no scheme at all and was, until this was added, the single most consequential blind spot here. What's still invisible: a bare hostname string with no scheme and no `@` (e.g. a raw `host`/`target` field), or a destination assembled by concatenating several argument fields at runtime. Bare-hostname detection was deliberately **not** added alongside the email case: a generic "this string looks like a hostname" heuristic (unlike an anchored email-address pattern) risks matching an ordinary filename or version string and incorrectly `BLOCK`ing a legitimate call — an unacceptable false-positive cost for a hard gate. An integrator who assumes "allowedOutboundHosts covers all my EXFIL sinks" because it's configured is still wrong the moment one of those sinks expresses its destination as anything other than a URL or an email address.
- **Exact hostname match only, by default.** An array allowlist does not do subdomain or wildcard matching — `"example.com"` does not also permit `"sub.example.com"`. This is deliberately strict (a permissive default here would be the more dangerous mistake), but it means a legitimate use of subdomains needs either every subdomain listed explicitly or a predicate function, and this library cannot verify a supplied predicate matches only what the integrator actually intends.
- **DNS-level and redirect-chain smuggling are out of scope entirely.** A hostname that resolves, via DNS trickery, to an attacker-controlled IP is indistinguishable from a legitimate one at this layer — the check only ever looks at the string in the argument, never performs a real network resolution or follows a request. Likewise, an allowlisted host that itself redirects the request elsewhere (a compromised or attacker-influenced allowed service) is invisible: this library mediates the tool-call *argument*, not the actual HTTP transaction a tool's `execute()` goes on to perform.
- **A channel that never passes through a broker-mediated tool call at all is unreachable, the same way GAPS.md #1 already names.** If the model's own conversational output (not a tool call) contains something a client will auto-fetch or render — a markdown image URL, for instance — the broker never sees it, allowlist or not. This is the outbound-direction analog of #1's untracked-context-injection channels, and has the identical fix: there isn't one at this layer; it has to be handled wherever that output actually reaches a client.
- **Over-detection (false positive): no notion of which argument is the actual destination — narrowed, now wired end-to-end.** `findOutboundHosts()` scans every string value anywhere in an EXFIL call's argument tree by default, not just the argument that is actually the call's destination. A benign field whose value happens to be, in its entirety, a valid `http(s)` URL or well-formed email address (e.g. a Slack `text` body that is exactly `"https://internal-wiki.example/kb/42"`) is indistinguishable from a real destination and trips the same unconditional hard `BLOCK` (DESIGN.md §7.4) as a genuine disallowed egress target, even though the tool never actually contacts that host. `findOutboundHosts(args, { destinationKeys: [...] })` accepts an optional `destinationKeys` list naming the argument key(s) that actually carry a tool's destination; when supplied, only those keys' subtrees are scanned, eliminating false positives from unrelated fields. **This is now wired into `BrokerOptions.allowedOutboundHosts` itself**: `ToolExecutor` gained an optional `destinationKeys?: readonly string[]` field (`src/types.ts`), declared on the tool at registration time — the same "travels with the tool, no per-call config" shape as `isSource`/`trusted`/`readsPrivateData`/`mayCallSummarize` — and `broker.ts`'s `gateDecision()` now calls `findOutboundHosts(argsSnapshot, { destinationKeys: tool.destinationKeys })` at its EXFIL gating call site, instead of the unscoped `findOutboundHosts(argsSnapshot)` it used before. A tool that leaves `destinationKeys` unset gets the original whole-tree scan exactly as before this field existed — purely additive, no existing registered tool's behavior changes. An integrator no longer has to bypass the broker's own egress check and call `findOutboundHosts` directly to get this narrowing; declaring `destinationKeys` on the tool itself is now sufficient. Bare-hostname detection remains deliberately unimplemented, for the reason named above: a generic "looks like a destination" heuristic risks being even riskier than the false positives it would fix.
- **`destinationKeys` assumes a fixed, singular destination key per tool — a call whose real destination varies by call shape can silently exempt itself from the allowlist entirely, narrowed via a new opt-in advisory.** `ToolExecutor.destinationKeys` (`src/types.ts`) is documented as "a fixed property of that tool's own schema, not something that varies call to call" — a webhook tool's `url`, always. A real tool can still violate that assumption: a generic `notify` tool whose destination lives under `slackUrl` for one call shape and `emailAddress` for another. Declaring `destinationKeys: ['slackUrl']` for such a tool doesn't just narrow the scan imperfectly for the `emailAddress`-shaped calls — it silently EXEMPTS every one of them from `allowedOutboundHosts` entirely, since `findOutboundHosts()` was never asked to look at `emailAddress` at all. This is a materially worse failure than the over-detection bullet above: over-detection produces a false `BLOCK` on a benign call, an availability cost that is loud and immediately noticed; this under-declaration produces a false `ALLOW` on a genuine, unapproved egress, silently, with no error — and because `allowedOutboundHosts` is often the SOLE check standing between an otherwise-policy-permissive (`CLEAN`) scope and a real network egress (§7.2's ordinary taint policy never looks at destination content at all), this isn't an ordinary defense-in-depth loss, it can be a complete, silent removal of the only check in effect for that call. `createBroker({ warnOnLikelyDestinationKeysMismatch: true })` is a new opt-in, purely advisory heuristic mirroring `warnOnLikelyUnmarkedSource`/`warnOnLikelyUnclassifiedSink` above (GAPS.md #1/#10): for a tool that declares a non-empty `destinationKeys` and whose call has already cleared the real `allowedOutboundHosts` gate (never for one already `BLOCK`ed — that call already has its own audit event), it separately scans the same call's arguments, via the new `findOutboundDestinationsOutsideKeys()` (`taint/egress.ts`), for a URL- or email-shaped value anywhere OUTSIDE every declared key's subtree, and flags one via an `ALLOW_WITH_WARNING` `AuditEvent` naming the exact offending argument path. Like its two siblings, it cannot verify a declaration against a tool's real behavior — it can only flag the concrete, observable symptom (a destination-shaped string sitting outside the declared keys on THIS call) and is subject to the identical over-detection tradeoff `findOutboundHosts()`'s whole-tree default already has: a benign field that happens to be, in its entirety, a URL or email address unrelated to the tool's real destination can false-positive here too. It never changes the gating decision, `destinationKeys` itself, or what's registered. See `BrokerOptions.warnOnLikelyDestinationKeysMismatch`'s own doc comment (`broker.ts`) and `test/broker.spec.ts`'s dedicated describe block for the worked example and the regression coverage confirming the gating decision is unaffected either way.
- **Under-detection (false negative), now fixed: a destination hidden inside a `Map` or `Set` used to be completely invisible.** `findOutboundHosts()`'s tree walk handled `Array.isArray(node)` explicitly but fell back to `Object.entries(node)` for everything else, which returns zero entries for a `Map` or `Set` (their entries live in an internal slot, not an own-enumerable property) — a URL or email nested inside either sailed through unscanned, silently, with no error and no `ArgsTooDeepError` trip, defeating the "hard structural boundary... full stop" guarantee DESIGN.md §7.4 documents. The exact same failure mode `scanArgsForTaint()` (`taint/scan.ts`) already had and already fixed — see that module's own "not a theoretical gap" comment, which applies identically here: the broker's default `cloneArgs` is `structuredClone`, which preserves `Map`/`Set` intact, so a tool's args snapshot can legitimately carry one. `findOutboundHosts()` now has the same explicit `Map`/`Set` branches, inserted at the same relative position, walking a `Map`'s keys AND values (a Map key is ordinary data, just as plausible a place to smuggle a destination as its value) and a `Set`'s values — and correctly respecting whichever `destinationKeys` scoping mode is active at that point in the walk. See `test/egress.spec.ts`'s dedicated Map/Set describe block for the exploit this closes and the true-negative/`destinationKeys`-interaction coverage.

None of this makes the allowlist not worth using — it closes a real, common shape cleanly, and closes it as a hard structural boundary rather than an approval prompt (#7's fatigue risk). It is not, and was never meant to be, a general egress-classification system.

## 19. One broker instance = one session — not enforced, only documented

Every safety guarantee this library makes — the scope watermark, the Layer 2 fingerprint registry, and `withLock`'s call-ordering serialization (§8) — is per-`Broker`-instance in-memory state. There is no built-in mechanism that stops an integrator from constructing one `Broker` and routing two different, concurrent, unrelated agent sessions' tool calls through it (mistaking `BrokerOptions.sessionId` for a lookup/isolation key rather than what it actually is — a label copied into audit records). Doing so does not fail loudly:

- `withLock` still serializes every `call()` on the shared instance against every other `call()` on it, correctly per §8's own guarantee — but that guarantee was only ever meant to hold *within* one session. Applied across two sessions it just means one session's slow approval wait now blocks the other session's unrelated calls too (an availability bug, not a soundness one on its own).
- Far worse: the watermark and registry are *shared* state. One session reading untrusted content raises the *shared* watermark, which now gates the *other* session's calls too — either uselessly over-restrictive (the other session never went near anything untrusted) or, if that other session's own exposure would otherwise have kept things CLEAN, an integrator who works around the false-positive friction by loosening policy for that instance quietly reopens the very isolation the two sessions needed from each other in the first place.

This is the same category of gap as item 10 (sink/capability misclassification) and item 17's `mayCallSummarize` — a trust boundary the library documents and the integrator is responsible for respecting, not one it can verify from inside `call()` itself (a `Broker` instance has no way to know how many logical sessions its caller intends to route through it). Fixed for this release: `createBroker()` and `BrokerOptions.sessionId` in `broker.ts`, and `ToolCallBroker` in `types.ts`, all now carry prominent doc comments stating the one-instance-one-session rule and why violating it is unsafe rather than merely unconventional. No runtime enforcement is planned — there is no sound way to distinguish "one session reusing its broker across turns, as intended" from "two sessions sharing a broker, by mistake" from inside the library.

## 20. A `REQUIRE_APPROVAL` denied for lack of a configured `approvalChannel` was indistinguishable from one a real channel actively denied — fixed

`BrokerOptions.approvalChannel` is optional, and omitting it is a supported, fail-SAFE configuration: a `REQUIRE_APPROVAL` decision with no channel to consult is correctly treated as denied, never as `ALLOW` (`broker.ts`'s `dispatchGated()` forces `approvedByHuman` to `false` whenever `this.approvalChannel` is `undefined`). The bug was that this "nobody was ever asked" outcome was, in both the thrown `ToolCallBlockedError`'s message and the recorded `AuditEvent.verdict.reason`, byte-for-byte identical to a REAL, correctly-configured `approvalChannel` evaluating the exact same call and its `requestApproval()` returning `false` — a deliberate security decision. Both paths produce `approvedByHuman: false` for a `REQUIRE_APPROVAL` decision, and `finalizeGated()` used to build the audited reason and thrown message from the plain policy `reason` string either way, with nothing anywhere naming which of the two actually happened.

This is a real production debugging trap, not a hypothetical: an operator staring at a "denied" audit-log entry after deploying `createBroker()` without ever wiring up `approvalChannel` (a common state for an early integration, or a test/staging harness) had no way to tell, from the log alone, "a human/process looked at this and said no" apart from "this broker was never given anyone to ask" — two situations that call for very different next steps (go find out why the approver said no, versus go configure `approvalChannel` at all) but that produced identical text to chase.

**Fixed**: `finalizeGated()` (`src/broker.ts`) now appends a specific, distinguishing note — `" (no approvalChannel configured -- see BrokerOptions.approvalChannel)"` — to the policy's own `reason` text, but only in the genuine no-channel case: `decision.action === 'REQUIRE_APPROVAL' && !approvedByHuman && this.approvalChannel === undefined`. A real channel's denial (`approvalChannel` configured, `requestApproval()` resolved `false`) is completely untouched — the policy's own reason stands alone, exactly as before this fix. The note is threaded onto the existing reason, never replacing it, so nothing about `default-policy.ts`'s own composed `REQUIRE_APPROVAL` text (DESIGN.md §7.2) is lost. See `BrokerOptions.approvalChannel`'s own doc comment (`src/broker.ts`) and DESIGN.md §7.3's matching implementation note. `test/broker.spec.ts` has dedicated coverage constructing both scenarios against the identical underlying policy verdict (an EXFIL sink at `RAW_UNTRUSTED`) and asserting the resulting error message and `AuditEvent.verdict.reason` are genuinely different strings, with the no-channel note present in exactly one of the two.

## 21. `ToolCallBlockedError` did not carry the `TaintContext` that explained the block — fixed

Every gated call that reaches `finalizeGated()` (`src/broker.ts`) already computes a `TaintContext` — the matched fingerprint records (`matchedRecords`, each with its `argPath`), the scope's `scopeLevel`/`privateDataSeen` at decision time, `sinkClass` — in order to reach a `PolicyDecision`, and that same `TaintContext` is recorded on the `AuditEvent.taint` for the call. `ToolCallBlockedError` (`src/errors.ts`), the error thrown for any call that was not executed, previously carried only `call` and `decision` (the verdict/reason) — the `TaintContext` sitting right there in scope at the throw site was simply not attached.

This was a real integration friction, not a hypothetical: an integrator with a plain `try { await broker.call(...) } catch (err) { ... }` around a gated call had `err.decision.reason` (the policy's own prose) but no structured answer to "which upstream content actually triggered this" — which `TaintRecord`(s) the blocked call's arguments matched, and where. Getting that required separately wiring a `BrokerOptions.auditSink` and correlating its events back to this specific call by `call.id`, an entirely reasonable thing to do for durable audit logging but a needless indirection for a `catch` block that already has the failing call in hand.

**Fixed**: `ToolCallBlockedError` gained a new `readonly taint: TaintContext` property, populated at its one construction site (`finalizeGated()`) from the exact same `auditTaint` value used to build that call's `AuditEvent.taint` — so `err.taint` and the corresponding audit record's `taint` are always the identical object, never independently re-derived. See `ToolCallBlockedError`'s own doc comment (`src/errors.ts`) and DESIGN.md §7.3.

**Not typed optional** — unlike a field added to a public *interface* this library's own `1.0.0` SemVer commitment (see CHANGELOG.md's header) requires treating as optional for API stability (`TaintContext`, `AuditEvent`, `PolicyDecision`, `BrokerOptions`, ...), `ToolCallBlockedError` is a concrete class only ever constructed inside this library (`grep`-confirmed: `finalizeGated()` is its sole `new ToolCallBlockedError(...)` call site); no external code structurally implements its shape the way a hand-built `TaintContext` fixture might, so there is no pre-existing external construction site a required field could break.

## 22. `AuditEvent` recorded WHEN a `REQUIRE_APPROVAL` verdict was reached, but not WHEN the approval wait started — so approval latency was uncomputable — fixed

`AuditEvent.at` (`src/types.ts`) is a single instant: when the FINAL verdict — granted, denied, or a `revalidateBeforeExecute()`-driven escalation — was recorded. For an ordinary `ALLOW`/`BLOCK`/`QUARANTINE_AND_RETRY` verdict that's the whole story, since nothing in between is worth timing. For `REQUIRE_APPROVAL`, though, `dispatchGated()` (`src/broker.ts`) deliberately releases the broker lock and waits — potentially for a human-timescale duration — on `ApprovalChannel.requestApproval()` (§ "a stale gating decision could still execute" in DESIGN.md's §4.1 implementation notes) before `at` is ever stamped. An integrator watching `AuditSink` for how long approvals actually take — a real operational question: is the approval queue backed up, is one particular reviewer slow, is the whole approval flow adding unacceptable latency to an agent loop — had no way to answer it from the audit trail alone, since nothing recorded when that wait began.

**Fixed**: `AuditEvent` gains a new field, `requestedAt?: number`, set in `dispatchGated()` immediately before phase 2 (the unlocked approval wait) begins — whether or not `BrokerOptions.approvalChannel` is actually configured to consult (the no-channel fail-safe case still resolves through the identical code path, just synchronously; see that field's own doc comment for why a near-zero latency there is still worth recording, not worth hiding). `event.at - event.requestedAt` is now exactly the approval latency for that call. Set ONLY on the `REQUIRE_APPROVAL` path — every other verdict leaves it `undefined`, the honest default (never a synthetic `0` or a copy of `at`), since for those verdicts there genuinely was no wait to time. See `AuditEvent.requestedAt`'s own doc comment (`src/types.ts`) and `test/broker.spec.ts`'s `AuditEvent.requestedAt` describe block for the granted/denied/no-channel coverage, each verified to fail before this field existed.

**Typed optional, not required** — the identical reasoning item 21 above gives for why a new field on an already-public *interface* (as opposed to a class this library alone constructs) must stay optional under this project's `1.0.0` SemVer commitment (CHANGELOG.md's header): `AuditEvent` is the parameter to every `AuditSink.record()` call, a public integrator-facing shape, so a required field here would be exactly the breaking change that policy rules out short of a major bump.

## 23. `TaintScope.id` existed but was never surfaced into `TaintContext`/`AuditEvent`, so an integrator watching the audit trail had no way to group events by turn — fixed

`TaintScope.id` (`src/types.ts`) is a fresh `randomUUID()` minted at broker construction and again by every `resetScope: 'turn'`/`'turn-decay'` turn-boundary reset (`clearScopeForTurnReset()`, `src/broker.ts`) — but it was only ever exposed via `broker.scope.id` for a caller with a live reference to the broker itself, never threaded into `TaintContext` or the resulting `AuditEvent`. An integrator watching only the audit trail (a durable log, a separate monitoring process with no broker reference at all) who wanted to compute a per-turn or per-turn-decay-episode block rate, or simply group "which events happened in the same exposure episode," had to thread the current scope id through their own orchestration code and correlate it back to each event by hand — the same "how would I even do this well" gap `broker.scope.id` already existed to close for a direct caller, left unaddressed for anything reading only `AuditSink`.

**Fixed**: `TaintContext` gains a new field, `scopeId?: string`, populated at every `TaintContext` construction site in the library — `broker.ts`'s `buildTaintContext()` (the real dispatch path) and its `ArgsTooDeepError` audit path, both `internal-audit.ts` call sites (`trivialTaintContext()`/`recordTrivialAudit()`, now threading `id` alongside `level`/`privateDataSeen`), and both `quarantine.ts` sites (via `CreateQuarantineOpts.getScope()`, likewise extended to also return `id`) — the identical set of five call sites item 22's sibling PR's `hasUnattributedSubstantialContent` field already touched. One deliberate exception, documented at its own site: `clearScopeForTurnReset()`'s own turn-reset `AuditEvent` names the id of the scope just DISCARDED, not the fresh one created to replace it — mirroring `taint.scopeLevel` on that same event already reporting the prior, pre-clear level rather than the resulting `CLEAN`. `declassify()`, by contrast, does not mint a new scope at all (`declassifyScope()` mutates the watermark in place), so its own audited `scopeId` — and every later call's, until the next real turn-boundary reset — is unchanged from before the clear. See `TaintContext.scopeId`'s own doc comment (`src/types.ts`) and `test/broker.spec.ts`'s `TaintContext.scopeId` describe block, which verifies grouping-by-scopeId across ordinary calls, the turn-reset event's discarded-not-new id, `declassify()`'s unchanged id, and `broker.summarize()`'s own audit events — each verified to fail before this field existed.

**Typed optional, not required** — the same `1.0.0` API-stability reasoning as item 22 above and `TaintContext.hasUnattributedSubstantialContent` before it: `TaintContext` is the parameter type every `PolicyFn` receives, a public integrator-facing interface, so a required field here would break a hand-built `TaintContext` fixture in an existing custom `PolicyFn`'s own test suite — exactly the shape change `1.0.0` rules out short of a major bump.

## 24. `AuditEvent.call.args` reached every configured `AuditSink` as raw, unredacted argument content — no seam to keep sensitive values out — mitigated via an opt-in hook

Every gated call (`BLOCK`ed or not) builds an `AuditEvent` whose `call.args` is the tool call's actual, cloned argument object (`broker.ts`'s `dispatch()`, `argsSnapshot`) — nothing redacted, truncated, or otherwise transformed it before `auditSink.record()` received it. This stood in sharp contrast to the Layer 2 fingerprint registry (§4.2), which deliberately never stores raw plaintext at all, only content-addressed `Fingerprint`s (`exactHash`/`simhash`/`shingleHashes` — see `TaintRegistry`'s own doc comment, `types.ts`) — a real design choice specifically so the registry is never a place raw sensitive content accumulates. `AuditEvent.call.args` bypassed that protection entirely: whatever a tool call's real arguments were — a credential passed to an authenticated API call, an API key, a large verbatim excerpt of a private document a `readsPrivateData` tool just fetched — went straight from the live call into whatever durable store, log shipper, or dashboard an integrator's `BrokerOptions.auditSink` forwards `AuditEvent`s to, with no seam for an integrator to intervene.

This is a different gap from item 12's own "`AuditEvent` JSON-safety" note above (`serializeAuditEvent()`, already fixed): that one is about a `TaintRecord.fingerprint`'s non-JSON-safe fields (`bigint`/`Uint32Array`) crashing a naive `JSON.stringify(event)` call — a serialization concern. This one is about the *content* of `call.args` itself reaching the sink unredacted — a confidentiality concern, present regardless of whether the configured sink ever touches `JSON.stringify` at all.

**Mitigated**: `BrokerOptions.redactAuditArgs?: (call: ToolCall, taint: TaintContext) => unknown` (`src/broker.ts`) lets an integrator supply a function applied to `call.args` ONLY, on every constructed `AuditEvent`, before it reaches `auditSink.record()` — replacing the value that ends up on the recorded event. Deliberately **not** a built-in PII/secret detector this library ships and enables by default — the same "integrator declares, library enforces" trust boundary item 10's sink/capability misclassification and item 17's `mayCallSummarize` already rest on: this library has no way to know what counts as sensitive in an integrator's own tool arguments, and a built-in heuristic redactor would risk both false negatives (a secret shaped unlike anything it was built to recognize) and false positives (redacting content a human approver or a later `AuditSink` consumer genuinely needed to see to make sense of a decision). `docs/audit-redaction.md` documents worked patterns instead — redacting by `taint.sinkClass`, redacting by cross-referencing `TaintContext.privateDataSeen`, and a simple key-denylist.

Implemented as a single wrapped `AuditSink` built once at broker construction (`withRedactedAuditArgs()`, `src/broker.ts`) rather than threaded individually through each of the roughly dozen `auditSink.record()`/`recordTrivialAudit()` call sites across `broker.ts`/`internal-audit.ts`/`quarantine.ts` — so a call site added later inherits redaction automatically, without anyone having to remember to wire it in there specifically. Unset (the default) is byte-for-byte today's behavior: `call.args` reaches the sink completely unchanged. **Typed optional, matching every other `BrokerOptions` field** — `redactAuditArgs` is a new field on the already-public, integrator-facing `BrokerOptions` interface (`src/index.ts`), so per the same `1.0.0` API-stability reasoning items 21–23 above already give, a new field there could never be typed required without breaking the SemVer commitment `1.0.0` makes short of a major bump; here that requirement lines up with the feature's own design anyway (a genuinely opt-in seam, identity when absent), but it is worth naming explicitly rather than assuming the two reasons always coincide. See `test/broker.spec.ts`'s `redactAuditArgs` describe block for the regression coverage — a configured redactor's replacement value reaching the raw sink instead of the original, and an unset one leaving `call.args` byte-identical to the unredacted original — both verified to fail before this field existed.

## 25. No tooling to explain, in plain language, why a session got gated the way it did — and the default `AuditSink` is a silent no-op most integrators won't notice until they need one — mitigated via `src/debug.ts`

Two related, previously-undocumented gaps, both about the DISTANCE between "this library faithfully records what happened" and "a human can actually see why."

First: `AuditEvent` (`types.ts`) and `TaintScope.watermark.sources` (the `ProvenanceTag[]` every watermark raise already appends to, §4.1) were always faithfully populated — nothing about the underlying data was missing or wrong — but neither was ever rendered into anything a human could read at a glance. An integrator debugging a blocked session had to hand-correlate raw `AuditEvent` objects themselves: which tool call raised the watermark, when, what the policy's `reason` actually said for a given verdict, how long a `REQUIRE_APPROVAL` wait actually took. None of that required new tracking — every field needed was already there — it just had no renderer.

Second, and sharper: the default `AuditSink` an integrator gets by configuring nothing at all — including by following README.md's own Quick start literally verbatim, which calls `createBroker()` with no `auditSink` option — is `broker.ts`'s `NOOP_AUDIT`, a silent no-op. Every gated decision is still enforced correctly either way (auditing is pure observability, never part of the gate itself, so this was never a soundness gap), but a broker constructed exactly as the Quick start shows produces ZERO audit trail, with nothing in the API surface surfacing that fact — an integrator who never reads this far into the docs, or who copies the Quick start into a real deployment without noticing `auditSink` is missing, has no record of anything this library ever gated, blocked, or approved.

**Mitigated**: `src/debug.ts` (also exported from `src/index.ts`) ships three pure helpers, none of which track anything new — every one is a renderer or aggregator over data this library was already faithfully collecting:

- `formatAuditTrail(events: readonly AuditEvent[]): string` — renders a session's `AuditEvent`s as readable, timestamped, one-line-per-event plain-language prose (tool name, a best-effort argument summary, verdict, the scope watermark level the decision was made against, whether the call executed, and the policy's own `reason` when present).
- `explainWatermark(scope: TaintScope): string` — renders `scope.watermark.sources` into one or a few sentences explaining which tool call(s) raised the current watermark level, and when, using exactly the `ProvenanceTag` data §4.1 already collects on every scope.
- `AggregatingAuditSink` — a small, dependency-free `AuditSink` (no new runtime dependency; `package.json` still has none) that wraps an optional delegate `AuditSink` and accumulates `verdict.action`-by-`taint.sinkClass` counts, `REQUIRE_APPROVAL` grant/deny counts (derived from `AuditEvent.executed`), `QUARANTINE_AND_RETRY` offer counts, and `AuditEvent.requestedAt`-derived approval latency (total and average), exposed via `snapshot(): Record<string, number>` for an integrator to render into their own Prometheus/Datadog/log format.

None of this closes the second half of the gap automatically — an integrator still has to actually configure `auditSink` (optionally `new AggregatingAuditSink(myRealSink)`) for any of it to have anything to work with; `createBroker()` with no options still defaults to `NOOP_AUDIT` exactly as before, unchanged, since silently swapping in a different default would itself be a behavioral change this library's `1.0.0` SemVer commitment rules out. What this closes is the SURFACING of that default: `AuditSink`'s own doc comment (`types.ts`), README.md's Core model section, and this entry now all name the no-op default explicitly, rather than leaving it to be discovered the hard way. See `src/debug.ts`'s own file-header and per-export doc comments for the full reasoning, and `test/debug.spec.ts` for regression coverage of all three exports against real `broker.call()` sequences.

## 26. `jsonSafeClone()` corrupted a clone's actual prototype instead of copying a source object's own `"__proto__"`-named key — found by property-based testing, fixed

`jsonSafeClone()` (`json-safe-clone.ts`, GAPS.md #16's opt-in fast alternative to the default `structuredClone`-based args cloner) built its output object with a plain bracket assignment, `out[key] = clonedValue`, for every key on the source object. For almost every key this is fine. But a source object can carry a genuine OWN, enumerable property literally named `"__proto__"` — not via the object-literal `__proto__:` shorthand (which sets the prototype and creates no own property at all), but via computed-property syntax (`{ ["__proto__"]: someValue }`) or `Object.defineProperty`, both of which create a real own data property that shadows `Object.prototype`'s inherited `__proto__` accessor for READS. `Object.keys()` correctly listed it, and reading it off the source correctly returned the own value — the bug was entirely on the WRITE side: `out` is a fresh `{}` with no own `"__proto__"` property yet to shadow that inherited accessor, so `out["__proto__"] = clonedValue` hit the accessor's SETTER instead of creating an own property, silently reassigning `out`'s actual prototype to `clonedValue` (or silently doing nothing, if `clonedValue` wasn't an object/null) rather than faithfully copying the key. The resulting clone had a corrupted, unintended prototype chain and was missing the `"__proto__"` key entirely from `Object.keys()` — a real, if narrow, prototype-integrity defect in a utility whose whole job is producing a faithful, fully independent copy.

Found by `test/json-safe-clone.property.spec.ts` (added earlier in this same release), not by hand-written test cases or either adversarial review pass — `fc.jsonValue()`'s generated inputs are unbiased toward any particular key name, and eventually shrunk to exactly this shape (`[{["__proto__"]:{}}]`) on the "idempotent under re-cloning" property: the FIRST clone's corrupted prototype made the SECOND clone attempt fail `isPlainObject()`'s check entirely, throwing instead of round-tripping. This is exactly the textbook property-based-testing payoff GAPS.md #8 already named for the fingerprint module's own two Unicode bugs — an input shape nobody thought to hand-write a test for.

**Fixed**: the clone loop now uses `Object.defineProperty(out, key, { value, writable: true, enumerable: true, configurable: true })` for every key, `"__proto__"` included — `Object.defineProperty` always creates/overwrites an own data property regardless of the key name, sidestepping the inherited accessor entirely, with the identical descriptor shape (writable/enumerable/configurable, all `true`) a plain assignment on a fresh object already produces for every other key. A new hand-written regression test in `test/json-safe-clone.spec.ts` pins this specific shape directly (verified fail-before/pass-after via `git stash`), alongside the property test that found it, which now passes cleanly across repeated runs.

This is narrowly scoped: `jsonSafeClone()` is opt-in (`BrokerOptions.cloneArgs`), not the default cloner (`structuredClone` is), and the defect required a source object with a specifically-crafted own `"__proto__"` key to trigger — but it was a real, previously-undetected prototype-pollution-shaped bug in code this library ships, so it's recorded here rather than treated as a one-line fix not worth naming.

## 27. `broker.summarize()`'s output was trusted unconditionally — no check that the Q-LLM's extraction was actually grounded in its source — narrowed via an opt-in `checkFieldGrounding()`

This section 4's own caveat restated precisely: a narrow, typed extraction schema shrinks what the Q-LLM can say, but nothing previously checked whether what it DID say was actually *true to the source* — a capability-less Q-LLM can plainly hallucinate a field value, or, if manipulated by a payload embedded in the very content it was asked to summarize, be steered into FABRICATING one that appears nowhere in the source at all. `quarantine.ts`'s own input-provenance check (§6.2 step 1, this section above) validates that the quarantine call's INPUT resembles its claimed source; it says nothing about whether the Q-LLM's OUTPUT reflects that input, and `createQuarantine()`'s `summarize()` unconditionally registers whatever `impl()` returns. A fabricated field previously sailed straight through registration and landed at `DERIVED_UNTRUSTED` completely indistinguishable from a genuine extraction.

`checkFieldGrounding(fields, sources, opts?)` (`src/grounding.ts`, exported from `src/index.ts`) narrows this, opt-in: given the original source text(s) and a Q-LLM's structured extraction result, it reports per field whether that field's value is fuzzy-traceable back to any source, reusing this library's own Layer 2 primitives (`overlapCoefficient`/`wordShingles`/`shingleHashesOf`) rather than a new similarity algorithm. Like Layer 2 fingerprint matching itself, it is standalone and never load-bearing — nothing in `broker.ts`/`quarantine.ts` calls it automatically, and this library does not decide what an ungrounded field means for your extraction (reject / re-extract / flag for review) — that stays the integrator's call, per this document's own #10 framing ("integrator declares, library enforces"). Three limits are worth naming directly, since they're the same shape of honesty this document already applies elsewhere: (1) it inherits GAPS.md #8's short-excerpt false negative more consequentially here than anywhere else in this library — a field value shorter than `SHINGLE_WIDTH` (5) words can be genuinely present in the source yet score exactly 0, since it shingles at a narrower width than the (typically much longer) source text and shares no shingle STRING with it; (2) an unusually long fabricated field checked against an unusually short source inherits the identical `overlapCoefficient` min()-denominator risk `quarantine.ts` itself declined to accept `overlapCoefficient` for, in its own provenance check, for exactly this reason; (3) "grounded" proves a value is textually PRESENT in the source, not that it is TRUE — a false claim an attacker plants directly in the source text itself (rather than getting the Q-LLM to invent something absent from it) still, correctly, scores as grounded, since closing that is the watermark/gating mechanism's job, not a field-level presence check's. See `src/grounding.ts`'s own doc comment for the full reasoning and `test/grounding.spec.ts`/`examples/quarantine-grounding-check.ts` for worked positive/negative cases.

## 28. The taint lattice orders trust *degree*, not source *class* — a user's own document, a third-party MCP server, and an arbitrary fetched web page are policy-indistinguishable once all three land at the same `TaintLevel`

`TaintLevel` (`CLEAN < DERIVED_UNTRUSTED < RAW_UNTRUSTED`) is a totally-ordered *degree* axis — how far a piece of content is from provably clean — used uniformly for both the scope watermark and Layer 2 fingerprint records (DESIGN.md §4.0). It is not, and was never designed to be, a *source-class*/*origin-type* axis: an internal, same-organization MCP server; a public, arbitrary web page; and text the user typed directly into the conversation all collapse to `RAW_UNTRUSTED` the moment any of them is read by an untrusted (non-`trusted`) source tool, and every `PolicyFn` — including `defaultPolicy` — sees only that single collapsed level. `ProvenanceTag.toolName`/`.note` (`src/types.ts`) do carry the originating tool's identity and a human-readable note into the audit trail, but only informally: no `PolicyFn` is handed a structured, policy-visible signal distinguishing *why* a source is untrusted, only *that* it is and *how strongly* (Layer 2 fingerprint confidence). This is a real, deliberate simplification, not a bug — collapsing "how untrusted" onto one totally-ordered number is exactly what keeps the watermark comparison in §7's decision table a single `LEVEL_ORDER[...]` lookup rather than a policy needing to reason about an open-ended set of source categories — but it means an integrator cannot express "treat our own internal MCP server's output as lower-risk than a random fetched URL, even though both are technically untrusted" without hand-rolling it entirely outside this library (e.g. running two brokers, or declaring the internal server's tools `trusted: true` outright, which drops taint tracking for it completely rather than tracking it at a *reduced* level). This is a genuinely different axis from the `privateDataSeen` "lethal trifecta" escalator (§7.2) — that rule is already implemented and fully orthogonal to source-class; nothing about this gap weakens it. Closing this would mean a new, additive `PolicyFn`-visible source-class field (on `ProvenanceTag`, most naturally) and — the harder design question — deciding whether `defaultPolicy` itself should ever branch on it, or whether it stays available only for an integrator's own custom `PolicyFn` to read, consistent with this document's #10 "integrator declares, library enforces" framing. Not yet built.

## 29. This project's own evaluation is a fixed, static corpus — it demonstrates nothing about robustness against an adaptive attacker who iterates against this specific defense mechanism

`corpus/cases.ts`'s 22 cases are hand-authored by this project's own maintainer, fixed at commit time, and run deterministically under `npm test` (README.md's "Injection corpus" section). Scoring cleanly against them demonstrates that `defaultPolicy` handles *those specific payloads* correctly — it says nothing about an attacker who knows (or can infer, since this is an open-source library) that the defense is a scope-watermark-plus-Layer-2-fingerprint broker, and crafts input specifically to exploit *that* mechanism rather than a generic prompt-injection template: staying just under a fuzzy-match confidence threshold (`QUARANTINE_MIN_FUZZY_SCORE`/`overlapMin`) rather than over it, splitting a payload across several fragments each individually below `UNATTRIBUTED_CONTENT_MIN_LENGTH` so no single fragment trips the decoy-match guard (§7.2, item above), or timing content injection to land just outside a `resetScope: 'turn-decay'` decay window. This is a genuinely different failure mode from #15's proxy-vs-causal-influence concern (which is about whether a *single* gated decision reflects the model's actual reasoning) and from #14's fuzzy-matching threshold tuning (which is about one mechanism's own tunable precision/recall tradeoff, not about generalizing from a fixed corpus to an adaptive adversary at all). Static, fixed-corpus evaluation against a known, published defense mechanism is a standard and well-understood limitation of security-tool self-evaluation generally, not specific to this library — but it is worth stating plainly rather than leaving `npm run corpus`'s "22/22 passed" output to be read as a robustness claim it was never designed to support. See #15's own "overclaiming disclaimer" heading for the sibling caveat this one is deliberately kept separate from.

## Not yet implemented (tracked, not silent)

All three items ever listed here — plan-freeze strict mode (`DESIGN.md` §11, `declarePlan()`), indexed registry storage (item 13 above), and `defaultPolicy` actually producing `QUARANTINE_AND_RETRY` (below, described in detail since — unlike the first two — it has no earlier numbered section of its own to point to) — are now implemented. This heading is kept so a future genuinely-unbuilt feature has a documented place to go, rather than being left to a stale TODO buried in code.

**`defaultPolicy` now produces `QUARANTINE_AND_RETRY` — but only under a specific, narrow trigger condition, and its limits are worth naming precisely (this used to be the entry recording that it was NOT yet implemented; it is now a description of what shipped instead).** `QUARANTINE_AND_RETRY` (`src/types.ts`) is offered IN PLACE OF an otherwise-`BLOCK`/`REQUIRE_APPROVAL` verdict (never alongside it) only when `TaintContext.matchedRecords` names a specifically identifiable untrusted source: an `'exact'` fingerprint match, or a `'simhash'`/`'shingle'` fuzzy match scoring at or above a deliberately conservative bar (`QUARANTINE_MIN_FUZZY_SCORE` in `src/policy/default-policy.ts`, well above `lookupFuzzy()`'s own default `overlapMin` — see that constant's own doc comment for why a bare pass of the registry's default fuzzy threshold isn't confident enough attribution to build this verdict's reason string around). A `'wrapper'` match (Layer 1's best-effort fast path, §4.3) and a `'quarantine-derived'` match (content already once through `summarize()` — offering to re-quarantine already-quarantined output would be circular) never count. `suggestedSchemaId` is always left `undefined` by `defaultPolicy` — see its own doc comment in `types.ts`: this library has no schema-registry concept for a policy to name a schema by id, so the entire actionable suggestion lives in `reason` instead.

The consequence worth naming directly, in the same "not load-bearing" register this document already uses for fingerprint matching elsewhere (items 8/9 above): **this is entirely gated on Layer 2 attribution succeeding.** A bare watermark taint with no `matchedRecords` entry at all — the common case for the load-bearing paraphrase-bypass scenario DESIGN.md §6.1 is built around, where Layer 1/2 both miss by construction — never triggers this; the ordinary `BLOCK`/`REQUIRE_APPROVAL` verdict stands, with nothing more actionable to say than before this feature existed. That is by design, not an oversight: offering `QUARANTINE_AND_RETRY` without a genuinely identifiable source to name would be an empty gesture (there would be nothing concrete for "re-run through `summarize()`" to even point at), and a HIGH-severity call (an unconditional `BLOCK`, e.g. `RAW_UNTRUSTED`/EXEC) is just as eligible as a lower-severity one when a qualifying match IS present — this verdict's presence or absence is purely an attribution-confidence question, never a severity downgrade. See `corpus/cases.ts`'s `quarantine-and-retry-offered` cases for a worked positive/negative pair through the real broker, and `test/policy.spec.ts` for the full unit-level trigger matrix.

**A qualifying match's mere presence used to be treated as sufficient — fixed, since a confirmed exploit showed it isn't.** A qualifying `matchedRecords` entry only ever established that SOME previously-registered untrusted text was present somewhere in the call's argument tree — `scanArgsForTaint()` walks every string leaf, with no check that the matched text has anything to do with the argument actually making the call dangerous. A call whose real dangerous content (e.g. a freshly-composed shell command) matched nothing in the registry could still qualify for `QUARANTINE_AND_RETRY` purely because an unrelated, previously-registered untrusted text was copied into a different, incidental argument (a `justification`/`notes` field, say) — a decoy. This was never a gating bypass (`QUARANTINE_AND_RETRY` is still never auto-executed, exactly like `BLOCK`), but the `reason` string named the decoy's source as the actionable fix, which could mislead a human approver or an integrator's own automation built to act on that field. `bestQuarantineCandidate()` (`src/policy/default-policy.ts`) now declines to substitute `QUARANTINE_AND_RETRY` when either of two structural guards trips: the qualifying matches name more than one distinct source record, or `TaintContext.hasUnattributedSubstantialContent` (a new `scanArgsForTaint()` signal, `taint/scan.ts`) is true — a string leaf of meaningful length elsewhere in the same call matched nothing at all, so the named match cannot be trusted to explain the whole picture. See `bestQuarantineCandidate()`'s own doc comment for the exploit and full reasoning, `test/policy.spec.ts`'s "decoy-match guards" tests, and `corpus/cases.ts`'s `quarantine-and-retry-decoy-match-not-offered` case.
